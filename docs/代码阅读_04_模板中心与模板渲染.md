## 1. 审核状态机

```text
          ┌──────── update(PUT) ────────┐
          ▼                             │
       draft ──submit──► pending_review ──approve──► approved ──disable──► disabled
          │                  │                                                │
       DELETE                └──reject──► rejected ──submit──┐                 │
          │                                   │  ▲           │                 │
          ▼                                   │  └─ update ──┘                 │
        （删除）                            DELETE                             │
                              pending_review ◄──────────── enable ─────────────┘
```

判定函数都在 `domain.TemplateStatus`：

| 方法 | 集合 | 用途 |
|------|------|------|
| `Editable()` / `CanSubmit()` | draft, rejected | `Update` / `Submit` 准入 |
| `CanReview()` | pending_review | `Approve` / `Reject` 准入 |
| `Usable()` | approved | **创建活动时唯一可引用的状态** |
| `Valid()` | 五个状态 | 列表查询参数校验 |

`Delete` 不复用 `Editable()`，而是直接判 `draft || rejected`（等价，但写死在服务层），并且是**硬删除**（`db.Delete` 无软删字段）。

`Enable` 的语义值得注意：`disabled → pending_review`，也就是**停用后重新启用必须再走一次审核**，不能直接回到 `approved`。

## 2. 服务层的统一套路

除 `Create`/`List`/`Get` 外，所有状态变更方法都是同一形状：

```go
tpl, err := s.Get(ctx, id)          // 不存在 → 40401
if !tpl.Status.CanXxx() {           // 状态不符 → 40902 InvalidState
    return nil, errcode.InvalidState
}
tpl.Status = 下一状态                // 内存里改字段
... 附带字段（RejectReason / ReviewedBy / ReviewedAt / UpdatedBy）
return s.updateCAS(ctx, tpl, in.Version)   // 乐观锁写库；冲突 → 40901 Conflict
```

`updateCAS` 允许调用方传入期望版本（`in.Version`），不传就用刚读到的 `tpl.Version`：

```go
func (s *Service) updateCAS(ctx, tpl, expected *int64) error {
    ver := tpl.Version
    if expected != nil { ver = *expected }
    ok, err := s.templates.UpdateCAS(ctx, tpl, ver)
    if !ok { return errcode.Conflict }
}
```

底层 SQL（[`repo/template.go`](../internal/adapter/repo/template.go)）：

```sql
UPDATE push_templates
SET code=?, name=?, body=?, biz_scene=?, channel_hint=?, status=?,
    reject_reason=?, updated_by=?, reviewed_by=?, reviewed_at=?,
    version = ? + 1
WHERE id = ? AND version = ?;
```

`UpdateCAS` 是**全字段覆盖**写。这意味着任何走 CAS 的操作都会把内存里的整个 `tpl` 刷回去；因为每次操作前都先 `Get` 了一遍，所以正常路径没问题，但如果将来有人复用 `UpdateCAS` 而不先读全量，会覆盖掉别人的字段。

`Update` 里还有一行容易漏看的副作用：

```go
tpl.RejectReason = ""   // 任何一次更新都清空驳回原因
```

## 3. Code 生成：并发安全的两步法

`code` 上有唯一索引，且允许业务不传（系统生成 `tpl_<id>`）。但 ID 要等插入后才知道，早期实现「空串先插」会让并发创建撞唯一键。现在的做法：

```go
// repo.Create：空 code → 先占一个绝对唯一的临时值
if tpl.Code == "" { tpl.Code = "tmp_" + uuid.NewString() }

// service.Create：插完再改成规范值
if in.Code == "" || strings.HasPrefix(tpl.Code, "tmp_") {
    repo.EnsureTemplateCode(tpl)          // tpl_<id>
    ok, _ := s.templates.UpdateCAS(ctx, tpl, tpl.Version)
    if !ok { return nil, errcode.Conflict }
}
```

后果与注意点：

- 若第二步失败（进程崩溃、CAS 冲突），库里会残留一条 `code = tmp_<uuid>` 的草稿。没有清理任务，需要人工处理。
- 显式传 `code` 时，`Create` 会先 `GetByCode` 查重复 → `40901`；真正的兜底仍是唯一索引（并发下会返回 GORM 原始错误，经 `response.Fail` 变成 `code=50001` 且 message 是原始 SQL 错误文本）。
- `template.FormatCode(id)` 与 `repo.EnsureTemplateCode` 都能生成 `tpl_%d`，前者目前没有调用方。

## 4. 活动如何引用模板：快照

创建活动时（[`campaign.Service.Create`](../internal/app/campaign/service.go)）：

```go
tpl, err := s.templates.GetByCode(ctx, in.TemplateID)   // template_id 是 code，不是数字 ID
if !tpl.Status.Usable() { return nil, errcode.TemplateNotUsable }  // 40903
task := &domain.MainTask{
    TemplateID:   tpl.Code,
    TemplateBody: tpl.Body,     // ★ 快照
}
```

之后整条链路都只用快照：Scheduler 把 `main.TemplateBody` 放进 `PushMessage.Body`，Pusher 渲染 `msg.Body`。所以：

- 活动创建后修改模板内容，**不影响已创建活动**。
- 活动创建后停用模板，也不影响已在跑的活动（只影响新建）。
- `template_id` 只是留痕，运行期不会再回查模板表。

`ChannelHint` 字段在整个发送链路里**没有任何消费方**，纯记录用途。

## 5. 渲染：`push.RenderTemplate`

```go
var varPattern = regexp.MustCompile(`\{\{\s*([a-zA-Z0-9_]+)\s*\}\}`)

func RenderTemplate(body string, vars map[string]string) string {
    if len(vars) == 0 { return body }              // ← 关键分支
    return varPattern.ReplaceAllStringFunc(body, func(m string) string {
        name := ...
        if v, ok := vars[name]; ok { return v }
        return ""                                   // 缺失变量 → 空串
    })
}
```

语义表：

| 场景 | 结果 |
|------|------|
| `vars` 为 nil / 空 map | **原样返回**，`{{name}}` 占位符保留在正文里 |
| `vars` 非空，变量存在 | 正常替换 |
| `vars` 非空，变量缺失 | 替换成**空字符串** |
| 变量名含中文/连字符等 | 正则不匹配，占位符原样保留 |
| `{{ name }}`（内部空格） | 匹配，`\s*` 允许 |

这个「空 map 保留占位符、非空 map 抹掉缺失变量」的不一致是已知行为（单测 [`internal/push/template_test.go`](../internal/push/template_test.go) 直接固化了它）。它与文档 03 的重推路径叠加会产生可见问题：重推新建的分片不带 `vars`，于是重发内容里会出现裸的 `{{name}}`。

变量从哪来：人群 Provider 返回的 `TargetUser.Vars` → Splitter 写进子任务 payload 的 `vars[user_id]` → Worker 放进 `PushMessage.Vars` → Gateway 渲染，并且同时把 `Vars` 原样透传给 `SendRequest.Vars`（供厂商模板参数使用）。

## 6. 列表查询

```go
List(q ListTemplateQuery)  // form 绑定：biz_scene / status / keyword / page / page_size
```

- `page_size` 默认 20，**上限 100**（超出被截断，不报错）。
- `keyword` 是 `code LIKE ? OR name LIKE ? OR body LIKE ?` 的三列模糊匹配，`%kw%` 前缀通配 → 无法命中索引，数据量大时是全表扫描。
- 排序固定 `id DESC`，用 offset 分页。
- `status` 非法值在服务层拦截为 `40001`。

## 7. 边界与坑清单

| # | 事实 | 影响 |
|---|------|------|
| 1 | `code` 临时值补写失败会残留 `tmp_*` | 需人工清理；列表里会看到奇怪的 code |
| 2 | `UpdateCAS` 全字段覆盖 | 复用时必须先读全量对象 |
| 3 | `Update` 会清空 `reject_reason` | 驳回原因不留历史 |
| 4 | 删除是硬删除 | 无审计、不可恢复；仅限 draft/rejected |
| 5 | `enable` 回到 `pending_review` | 停用再启用必须重审，业务流程要知情 |
| 6 | `channel_hint` 无消费方 | 只是元数据 |
| 7 | 快照机制 | 修模板不影响存量活动（优点），但也无法「热修」已创建活动的文案 |
| 8 | `vars` 为空时保留占位符 | 重推 / 无变量人群会把 `{{x}}` 发给用户 |
| 9 | 关键字搜索走 `LIKE %kw%` | 模板量大时性能差 |
| 10 | 审核接口无操作人鉴权 | `reviewed_by` 是调用方自报字段 |
