# 高 / 普通两级优先级队列 · 精读

本文说明 Starlink 如何用 **两条物理隔离的队列**（而非单队列内的优先级字段排序）实现事务（high）与营销（normal）分流。配套见 [`Scheduler层代码解析.md`](Scheduler层代码解析.md)、[`Pusher层代码解析.md`](Pusher层代码解析.md)。

---

## 1. 设计结论（先记住）

```text
不是：一个 Stream 里按 priority 字段插队
而是：high / normal 各一条独立 MessageQueue
       （独立 topic/stream + 独立 Consumer Group + 可独立扩容）
```

| 优先级 | 典型场景 | 默认 Stream | 默认 Group | Pusher 并发配置 |
|--------|----------|-------------|------------|-----------------|
| `high` | 支付、OTP、安全 | `starlink:push:high` | `pushers-high` | `high_worker_concurrency`（默认 32） |
| `normal` | 营销促销（默认） | `starlink:push:normal` | `pushers-normal` | `worker_concurrency`（默认 16） |

分流键落在 **活动级** `main_tasks.priority`，经 Scheduler 拷贝到每条 `PushMessage.Priority`，再由 `PriorityRouter.Publish` 写入对应物理队列。

## 2. 端到端数据流

```text
POST /campaigns
  priority? + biz_scene
        │
        ▼
  ResolvePriority → 写入 MainTask.Priority（落库，活动生命周期不变）
        │
        ▼
  Scheduler processSubTask
  每条 PushMessage.Priority = main.Priority.Normalize()
        │
        ▼
  mq.Publish([]PushMessage)   // Worker 注入的是 PriorityBroker
        │
        ├─ Priority.IsHigh()  → high.Publish
        └─ else               → normal.Publish
        │
        ▼
  Pusher
  -queue=all  → 同时 Consume High() 与 Normal()
  -queue=high → 只吃事务队列
  -queue=normal → 只吃营销队列
```

**同一子任务批次内优先级通常相同**（都来自同一主任务）；`Publish` 仍按条拆分，便于将来同批混优或重推边界情况。

## 3. 领域模型：优先级如何定

文件：[`internal/domain/priority.go`](../internal/domain/priority.go)

### 3.1 类型

```go
PriorityHigh   = "high"
PriorityNormal = "normal"  // 空串 Normalize() 后也是 normal
```

`IsHigh()`：仅 `Normalize() == high` 为真；其它一律走普通队列。

### 3.2 `ResolvePriority`（创建活动时）

```go
ResolvePriority(explicit, bizScene, highBizScenes []string) Priority
```

| 请求 `priority` | 结果 |
|-----------------|------|
| `"high"` / `"normal"` | **原样采用**（显式优先） |
| `""` 或不传 | `biz_scene ∈ high_biz_scenes` → high，否则 normal |
| 非法值 | Create 入口 `Valid()` 校验失败 → `InvalidParam` |

配置默认场景（[`configs/config.yaml`](../configs/config.yaml)）：

```yaml
mq:
  high_biz_scenes: [txn, otp, security, payment, transactional]
```

创建路径：[`campaign.Service.Create`](../internal/app/campaign/service.go)

```go
prio := domain.ResolvePriority(in.Priority, in.BizScene, s.highBizScenes)
task.Priority = prio  // 写入 main_tasks
```

之后 **改配置不会回溯已创建活动**；优先级以库中字段为准。

### 3.3 持久化与消息字段

| 位置 | 字段 |
|------|------|
| `MainTask.Priority` | DB 列，默认 `normal` |
| `PushMessage.Priority` | MQ JSON，决定进哪条物理队列 |

Scheduler 组装时：

```186:201:internal/scheduler/worker.go
prio := main.Priority.Normalize()
// ...
Priority: prio,
```

## 4. 端口分层：单队列 vs 双优先级门面

文件：[`internal/port/port.go`](../internal/port/port.go)

```text
MessageQueue          // 一条物理队列：Publish / Consume / EnsureReady
MessagePublisher      // Scheduler 只需要 Publish
PriorityBroker        // 门面：Publish 分流 + High()/Normal() + Driver/Close
```

| 角色 | 依赖接口 | 用法 |
|------|----------|------|
| Scheduler Worker | `MessagePublisher`（实际注入 `PriorityBroker`） | `Publish(msgs)` 一次调用，内部分流 |
| Pusher | `PriorityBroker.High()` / `.Normal()` | 拿到 **单队列** 再 `Consume` |
| bootstrap | `mq.Open` → `PriorityBroker` | 全进程共享 |

## 5. 装配：`mq.Open` → 一对队列 + Router

### 5.1 工厂约定

[`internal/adapter/mq/factory.go`](../internal/adapter/mq/factory.go)：

```text
Register(driver, Factory)   // 各驱动 init 注册
Open(deps) →
  factory(deps) → Queues{High, Normal}   // 驱动必须返回一对非 nil
  → NewPriorityRouter(driver, high, normal)
```

任何自定义驱动也必须返回 **两条** `MessageQueue`，否则 `Open` 报错。

### 5.2 各驱动如何造「一对」

| 驱动 | High | Normal |
|------|------|--------|
| `redis_stream` | `RedisStream(high.topic, high.group)` | `RedisStream(normal.topic, normal.group)` |
| `rocketmq` | `RocketMQQueue(highTopic, highGroup, transport)` | 同理 normal |
| `memory` | `MemoryQueue("high", buf)` | `MemoryQueue("normal", buf)` |

Redis 默认名见配置 defaults（[`config.applyDefaults`](../internal/config/config.go)）：缺省补 `starlink:push:high|normal` 与 `pushers-high|normal`；旧版单 `mq.stream/group` 仅回填到 **normal**。

### 5.3 配置结构

```yaml
mq:
  driver: redis_stream
  high:
    topic: "starlink:push:high"
    group: "pushers-high"
  normal:
    topic: "starlink:push:normal"
    group: "pushers-normal"
  redis_stream:
    maxlen: 100000
    ack_xdel: true
```

`TopicOrStream()`：驱动无关命名；Redis 下当 Stream 名，RocketMQ 下当 Topic。

## 6. 分流核心：`PriorityRouter`

文件：[`internal/adapter/mq/priority_router.go`](../internal/adapter/mq/priority_router.go)

### 6.1 结构

```go
type PriorityRouter struct {
    driver string
    high   port.MessageQueue
    normal port.MessageQueue
}
```

驱动无关：只做拆分与委托，**不解析** Redis/RocketMQ 细节。

### 6.2 `Publish`（写路径精读）

```53:76:internal/adapter/mq/priority_router.go
func (r *PriorityRouter) Publish(ctx context.Context, msgs []domain.PushMessage) error {
	var high, normal []domain.PushMessage
	for i := range msgs {
		if msgs[i].Priority.IsHigh() {
			high = append(high, msgs[i])
		} else {
			normal = append(normal, msgs[i])
		}
	}
	if len(high) > 0 {
		if err := r.high.Publish(ctx, high); err != nil {
			return fmt.Errorf("publish high: %w", err)
		}
	}
	if len(normal) > 0 {
		if err := r.normal.Publish(ctx, normal); err != nil {
			return fmt.Errorf("publish normal: %w", err)
		}
	}
	return nil
}
```

精读要点：

1. **先拆后写**：同批可拆成两个切片（当前业务同批通常纯 high 或纯 normal）。
2. **顺序**：先 high 再 normal；high 失败则 **不会** 写 normal（整次 Publish 失败 → Scheduler 子任务失败）。
3. **非事务跨队列**：high 已成功、normal 失败时，可能出现「部分用户已入 high、同批其余未入 normal」——调用方按整批错误处理，需靠失败重推/人工对齐（边界情况）。
4. 空切片不调用底层 Publish。

辅助方法：`Queue(p)` 按优先级取队列；`EnsureReady` 对 high、normal **都**建 Group/Topic。

### 6.3 `Consume` 的陷阱

```go
func (r *PriorityRouter) Consume(...) error {
    return r.normal.Consume(...)  // 只消费 normal！
}
```

Router 虽实现了 `MessageQueue`，但其 `Consume` **不会**吃 high。  
Pusher **禁止**对 Broker 直接 `Consume`；必须：

```go
infra.MQ.High().Consume(...)
infra.MQ.Normal().Consume(...)
```

这是有意设计：双队列要独立生命周期与并发参数，不能合成一个 Consume 循环。

## 7. 消费侧：Pusher 如何挂两条队列

[`cmd/pusher/main.go`](../cmd/pusher/main.go)：

```text
-queue=all     → 两个 goroutine：
                   Consumer(High,  high_worker_concurrency)
                   Consumer(Normal, worker_concurrency)
-queue=high    → 仅 High
-queue=normal  → 仅 Normal
```

| 能力 | 实现方式 |
|------|----------|
| 事务不被营销堵住 | 物理隔离；营销积压不影响 high Stream |
| 资源倾斜 | high 默认更高 concurrency（32 vs 16） |
| 分池部署 | 事务机只跑 `-queue=high`，营销机只跑 `-queue=normal` |
| 水平扩展 | 同 Group 多 Consumer（如 `pusher-xxxx-high`） |

**限流已按渠道×优先级分桶**：`channel_quota.high_reserve_ratio>0` 时 high/normal 不互抢；`distributed=true` 跨实例共享。仍建议生产用 `-queue=high`/`normal` 分进程隔离并发与故障域。

## 8. 与「单队列优先级」的对比（理解设计取舍）

| 方案 | 本仓库 | 典型单队列加权 |
|------|--------|----------------|
| 隔离 | 两条 Stream/Topic | 一条队列内排序/加权 |
| 积压 | 营销堵死不影响事务消费进度 | 需 broker 支持优先级投递或多级 |
| 运维 | 可对 high 单独扩容 / 告警 | 共用同一积压指标 |
| 实现复杂度 | Router 拆分 + 双 Consume | 依赖中间件特性 |
| 严格全局序 | **不保证**跨队列顺序 | 同队列内可更强 |

本实现追求的是 **SLA 隔离**，不是「全局按优先级插队到同一条流水线」。

## 9. 生命周期时间线（一条 OTP 活动）

```text
1. POST { biz_scene:"otp", priority 省略 }
2. ResolvePriority → high（命中 high_biz_scenes）
3. main_tasks.priority = high
4. Split / Claim 与优先级无关（DB 认领不区分 high/normal）
5. processSubTask：PushMessage.Priority=high
6. PriorityRouter → XADD starlink:push:high
7. Pusher high Consumer：XREADGROUP group=pushers-high
8. Gateway.Handle → 渠道发送（去重键不含 priority）
```

营销活动同理走 `starlink:push:normal` / `pushers-normal`。

去重键是 `(main_task_id, user_id, channel)`，**与队列优先级无关**——同一活动不会因进错队列而绕过去重。

## 11. 已知边界

| 点 | 说明 |
|----|------|
| 活动级固定 | 创建后改 `high_biz_scenes` 不影响已有任务 |
| Router.Consume 只吃 normal | 勿对 Broker 直接 Consume |
| Publish 跨队列非原子 | high 成功 + normal 失败的部分可见性 |
| 同进程双消费 | 并发共享 Gateway；配额已按 priority 分桶（需配置 `high_reserve_ratio`） |
| Scheduler 无优先级调度 | 子任务认领 FIFO；优先级只影响 **MQ 落点** |
| PEL/DLQ 按队列独立 | high/normal 各有 pending 与 `{topic}:dlq`；参数共用 `mq.redis_stream.*` |
| 容量治理共用配置 | 两条业务 Stream + 各自 DLQ 均受 `maxlen`/`dlq_maxlen`/`ack_xdel` 约束 |
