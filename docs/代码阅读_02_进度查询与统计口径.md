# 功能点 02 · 进度查询与统计口径

覆盖：`GET /campaigns/:id`、`/:id/progress`、`/biz/:biz_id` 的数据来源，以及「入队口径」与「渠道口径」两套计数如何共存。

主要源码：

- [`internal/app/campaign/service.go`](../internal/app/campaign/service.go) → `buildProgress`、`calcProgress`
- [`internal/adapter/repo/task.go`](../internal/adapter/repo/task.go) → `SummarizeSubTasks`、`CountUserOutcomes`、`ListFailedUserIDs`
- [`internal/scheduler/aggregator.go`](../internal/scheduler/aggregator.go) → `refreshUserCounts`

---

## 1. 两套口径先分清

这是整个项目最容易读错的地方。系统里有**两套并存**的成功/失败定义：

| 口径 | 谁写 | 存在哪 | 含义 |
|------|------|--------|------|
| 流水线口径（入队） | Scheduler | `sub_tasks.success_count/fail_count` + Redis `starlink:task:{id}:stats` | 消息是否成功写进 MQ |
| 渠道口径（用户级） | Pusher / 回执 | `push_records` | 用户是否真的被某个渠道成功投递 |

主任务表上的 `success_count/fail_count` 是**渠道口径的缓存**：由 `Aggregator.refreshUserCounts` 与 `callback.Handle` 调 `SyncMainUserCounts` 覆盖写入。而主任务的 `status`（success/partial/failed）仍是**流水线口径**的产物。

一句话记住：**status 说的是「都送进队列了吗」，success_users 说的是「渠道真发成功了几个人」。**

## 2. `buildProgress` 逐段

```text
1. SummarizeSubTasks(mainTaskID)  → 按状态分组的子任务与用户数
2. 填静态字段（渠道链、mode、priority、时间戳、finished=IsTerminal）
3. 遍历 summaries：
     pending/running/retrying → in_progress_users += UserTotal，分别记 SubPending/SubRunning/(subRetrying)
     success  → success_users += UserSuccess，SubSuccess
     failed   → fail_users    += UserFail，SubFailed
     partial  → 两个都累加（注意：不单独暴露 sub_partial 计数）
     cancelled→ cancelled_users += UserTotal，SubCancelled
4. 若有 pushRepo：CountUserOutcomes(mainTaskID)
     HasRecords=true → 用渠道口径**覆盖** success_users / fail_users
   否则回退主任务字段（只在为 0 时兜底）
5. TotalUsers==0 → 用 成功+失败+取消+在途 兜底
6. task.TotalCount>0（拆分已写入）→ 以它为准，反推 in_progress = Total - (succ+fail+cancel)
     终态：in_progress 归零；若是 cancelled 且没算出取消数，用剩余量补
7. calcProgress(...)
```

### 2.1 `SummarizeSubTasks` 的 SQL

```sql
SELECT status,
       COUNT(*)                        AS sub_count,
       COALESCE(SUM(total_count),0)    AS user_total,
       COALESCE(SUM(success_count),0)  AS user_success,
       COALESCE(SUM(fail_count),0)     AS user_fail
FROM sub_tasks WHERE main_task_id = ? GROUP BY status;
```

一次分组查询拿全部分状态计数，无 N+1。

### 2.2 `CountUserOutcomes` 的三步

```text
1. COUNT(*) push_records WHERE main_task_id=?   → HasRecords
2. COUNT(DISTINCT user_id) WHERE status IN (sent,delivered,clicked)  → SuccessUsers
3. ListFailedUserIDs(...) 的行数                                     → FailUsers
```

`ListFailedUserIDs` 的语义是「有失败流水**且**该活动下没有任何渠道成功」的用户：

```sql
SELECT DISTINCT f.user_id FROM push_records f
WHERE f.main_task_id = ? AND f.status = 'failed'
  AND NOT EXISTS (
    SELECT 1 FROM push_records s
    WHERE s.main_task_id = f.main_task_id AND s.user_id = f.user_id
      AND s.status IN ('sent','delivered','clicked')
  );
```

这正是 `fallback` / `parallel` 语义要求的：多渠道里任一成功即算用户成功，全失败才算失败。它同时被文档 03 的重推逻辑复用。

代价：`FailUsers` 是**把用户 ID 全捞回内存再取 len**，大活动上会有可观的传输量（`CountUserOutcomes` 在进度接口、聚合终态、回执、重推对齐四处被调用）。这是当前实现的一个性能待改点。

## 3. 百分比算法 `calcProgress`

```go
if status.IsTerminal()                          -> 100, "100.00%"
if (pending||paused) && totalUsers==0 && subTotal==0 -> 0
switch {
case totalUsers > 0: pct = finishedUsers / totalUsers * 100
case subTotal  > 0:  pct = subDone / subTotal * 100
default:             pct = 0
}
clamp 到 [0,100]，四舍五入两位
```

其中 `finishedUsers = success + fail + cancelled`（渠道口径的成功/失败 + 子任务口径的取消）。

后果：

- 终态一律 100%，包括 `failed` 和 `cancelled`。进度到 100% 不代表都成功。
- 拆分完成前 `total_count=0`、`sub_task_total=0`，进度显示 0%，属预期。
- 因为 `finishedUsers` 混用了两套口径（成功/失败来自流水，取消来自子任务），极端情况下三者之和可能超过 `total_count`；代码里对 `finished > TotalCount` 做了截断，但百分比本身没有做同样的截断前处理——`pct` 的 clamp 兜住了这一点。

## 4. 响应字段来源表

| 字段 | 来源 |
|------|------|
| `status` | `main_tasks.status`（流水线口径） |
| `total_users` | `main_tasks.total_count`（拆分收尾写入），未拆完为 0 后按兜底公式推算 |
| `success_users` / `fail_users` | 有流水时 = `push_records` 渠道口径；无流水时 = 子任务汇总，再兜底主任务字段 |
| `cancelled_users` | 子任务 `cancelled` 的 `SUM(total_count)`；终态 cancelled 时可能用剩余量补 |
| `in_progress_users` | `total_count - (succ+fail+cancel)`，终态归零 |
| `sub_task_total` / `sub_task_done` | 主任务字段（拆分收尾 / 聚合累加） |
| `sub_pending/running/success/failed/cancelled` | 子任务分组计数 |
| `sub_in_progress` | pending + running + retrying |
| `progress_percent` / `progress_text` | `calcProgress` |
| `finished` | `status.IsTerminal()` |
| `priority` / `channels` / `channel_mode` | 主任务落库值（`EffectiveChannelMode()` 运行时再归一） |

注意 `ProgressView` 里**没有** `sub_partial` 字段：子任务为 `partial` 时其用户数被计入 success/fail，但分片计数不体现在任何 `sub_*` 字段（`sub_in_progress` 也不含它）。实际上 Scheduler 只会把子任务写成 `success`/`failed`/`cancelled`，`partial` 目前不会出现在子任务上。

## 5. 谁在回写渠道口径

| 时机 | 代码 | 动作 |
|------|------|------|
| 主任务聚合到终态 | `Aggregator.refreshUserCounts` | `CountUserOutcomes` → `SyncMainUserCounts` |
| CAS 冲突且发现已终态/暂停 | 同上（提前 return 前也会刷一次） | 保证计数不落后 |
| 收到渠道回执 | `callback.Service.Handle` 末尾 | 同样 `CountUserOutcomes` → `SyncMainUserCounts` |
| 失败重推后 | `campaign.realignCounters` | 同步 `success/fail/sub_done/sub_total`，并 `SetSubDone` 对齐 Redis |

`SyncMainUserCounts` 只写两列，不动 `version`、不动 `status`，所以不会与终态 CAS 相互干扰。

## 6. 排查手册

```sql
-- 主任务视角
SELECT status, total_count, success_count, fail_count, sub_task_total, sub_task_done
FROM main_tasks WHERE id = 1;

-- 子任务分状态（等价于接口里的 sub_* 字段）
SELECT status, COUNT(*), SUM(total_count), SUM(success_count), SUM(fail_count)
FROM sub_tasks WHERE main_task_id = 1 GROUP BY status;

-- 渠道口径成功用户
SELECT COUNT(DISTINCT user_id) FROM push_records
WHERE main_task_id = 1 AND status IN ('sent','delivered','clicked');

-- 单个用户为什么没收到
SELECT channel, status, provider_id, error_msg, sent_at
FROM push_records WHERE main_task_id = 1 AND user_id = 'u_new_users_1';
```

```bash
# 流水线口径（Redis 聚合计数）
redis-cli HGETALL starlink:task:1:stats        # success / fail / done
redis-cli SMEMBERS starlink:task:1:sub_finished # 已计入完成的子任务 ID
```

如果出现「status=success 但 success_users < total_users」，通常是正常的：入队完成早于渠道发送完成，等回执或下一次 `CountUserOutcomes` 刷新即可；持续不涨才需要查 `push_records` 里的 `failed` 与 `error_msg`。

## 7. 已知限制

| # | 事实 | 影响 |
|---|------|------|
| 1 | `status` 与 `success_users` 口径不同 | 需要向业务方明确解释；若要求「全部送达才 success」需把聚合点搬到 Pusher/回执侧 |
| 2 | `FailUsers` 靠拉全部失败用户 ID 计数 | 大活动下开销偏高，且在四个调用点重复 |
| 3 | `partial` 子任务无独立计数字段 | 目前不会出现，但接口契约上是缺口 |
| 4 | 进度接口无缓存 | 每次查询打 2~3 条聚合 SQL，被前端轮询时需注意 |
