# 功能点 03 · 失败重推机制

覆盖：`POST /api/v1/campaigns/:id/retry` 的完整链路、可重推边界、以及为什么「渠道成功但业务失败」的用户重推不了。

主要源码：

- [`internal/app/campaign/service.go`](../internal/app/campaign/service.go) → `Retry`、`buildRetryShards`、`realignCounters`
- [`internal/adapter/repo/task.go`](../internal/adapter/repo/task.go) → `ResetFailedSubTasks`、`MaxShardIndex`、`ReopenMainTask`、`SyncMainCounters`、`ListFailedUserIDs`
- [`internal/adapter/redis/client.go`](../internal/adapter/redis/client.go) → `ClearDelivered`、`SetSubDone`

---

## 1. 一张图

```text
POST /retry
  │
  ├─ 1. Status.IsRetryable()? （仅 failed / partial）  否 → 40902
  │
  ├─ 2. ListSubTasksByStatus(failed) → 解析 user_ids → inFailedSubs 集合
  ├─ 3. pushRepo.ListFailedUserIDs() → 渠道口径失败用户
  ├─ 4. extraUsers = 渠道失败用户 − 已在失败分片里的用户
  │
  ├─ 5. ResetFailedSubTasks() → failed 子任务回 pending（retry_count+1，清 worker/错误/计数）
  ├─ 6. extraUsers 非空 → buildRetryShards() → CreateSubTasks（新分片）
  │
  ├─ 7. resetN==0 && newSubs==0 → 40004 nothing_to_retry
  │
  ├─ 8. 清 Redis dedup：对 inFailedSubs ∪ extraUsers × 活动全部渠道 ClearDelivered
  │
  ├─ 9. ReopenMainTask(addSubTasks=newSubs)   // WHERE status IN (failed,partial) → running
  │       └─ 失败（已被别人改状态）→ SyncMainCounters 兜底，保留原 fail_count
  │
  ├─ 10. realignCounters()：重算 done/total 与用户口径，并 SetSubDone 对齐 Redis
  └─ 11. 重读主任务 → RetryResult{status, reset_subs, new_subs, retry_user_count}
```

之后就交给 Scheduler：`ClaimSubTask` 会认领这些回到 `pending` 的分片，重新组装 `PushMessage` 投递。

---

## 2. 为什么要「两个来源」求并集

失败可能发生在两个不同层次：

| 失败层次 | 表现 | 来源 |
|----------|------|------|
| 入队失败 | 整个子任务标 `failed`（例如 `mq.Publish` 报错、解析 `user_ids` 失败） | `sub_tasks.status='failed'` |
| 渠道失败 | 子任务是 `success`（消息进了队列），但某些用户所有渠道都发失败 | `push_records.status='failed'` |

只重置失败子任务会漏掉第二类；只按流水补分片会重复覆盖第一类。所以代码取并集，并用差集避免重复：

```go
extraUsers = pushFailed 中不在 inFailedSubs 的用户
retryUsers = len(inFailedSubs) + len(extraUsers)   // 返回给调用方的 retry_user_count
```

注意 `retry_user_count` 是**估算值**：`inFailedSubs` 是失败分片里的全部用户，其中可能有人其实已经发成功（子任务整体失败但部分用户成功的情况）。

## 3. 新分片如何续号

```go
maxIdx, _ := tasks.MaxShardIndex(mainTaskID)   // 无子任务返回 -1
shard := maxIdx + 1
for i := 0; i < len(userIDs); i += batchSize { ... shard++ }
```

`batchSize` 取 `scheduler.batch_size`（API 进程通过 `campaign.Deps.BatchSize` 注入，默认 200）。新分片的 `UserIDs` 只有 `{"user_ids":[...]}`，**没有 `vars` 与 `channels`**：

- 个性化变量丢失 → 重推消息的 `vars` 为空 → `RenderTemplate` 在 vars 为空时**原样返回模板**，占位符 `{{name}}` 会出现在最终内容里（见文档 04）。
- 用户可达渠道丢失 → 走任务默认渠道链，不再做 `IntersectChannels` 求交。

这是重推路径与首次拆分路径的一个真实语义差，做个性化内容的业务需要注意。

## 4. 状态与计数如何收口

### 4.1 `ResetFailedSubTasks`

```sql
UPDATE sub_tasks SET status='pending', success_count=0, fail_count=0,
       finished_at=NULL, worker_id='', claimed_at=NULL, started_at=NULL,
       last_error='', retry_count = retry_count + 1
WHERE main_task_id=? AND status='failed';
```

`retry_count` 是唯一保留的历史痕迹，可用来判断某分片被重推过几次。

### 4.2 `ReopenMainTask`

```sql
UPDATE main_tasks SET status='running', finished_at=NULL, version=version+1
       [, sub_task_total = sub_task_total + ?]
WHERE id=? AND status IN ('failed','partial');
```

只接受 `failed`/`partial` —— 与 `IsRetryable()` 一致，`running` 不在其中。如果 CAS 没命中（并发下状态已变），走 `SyncMainCounters` 兜底：

```go
SyncMainCounters(id, task.SuccessCount, task.FailCount, task.SubTaskDone, task.SubTaskTotal+newSubs)
```

刻意传入**原有的** `FailCount`，避免把失败数抹零。

### 4.3 `realignCounters`

重推后 Redis 的 `done` 计数与 DB 不再一致（子任务从 done 回到 pending），必须对齐，否则聚合永远等不到 `done == sub_task_total`：

```text
遍历 SummarizeSubTasks：
  success            → done++, pipeSucc += UserSuccess
  failed             → done++, pipeFail += UserFail
  cancelled/partial  → done++, 两者都累加
  total += SubCount（含 pending/running）
用户口径：有 push_records 则用 CountUserOutcomes 覆盖
SyncMainCounters(id, userSucc, userFail, done, total)
cache.SetSubDone(id, pipeSucc, pipeFail, done)   // 同时 DEL sub_finished 集合
```

`SetSubDone` 的副作用很关键：它会 `DEL starlink:task:{id}:sub_finished`，从而让被重置的子任务再次 `TryMarkSubFinished` 成功、重新计入完成。

## 5. 去重标记为什么要清

正常路径上，Pusher 只在**成功**时 `MarkDelivered` 写 `starlink:dedup:{task}:{user}:{channel}`。失败不写标记，所以理论上重推无需清理。代码仍然显式 `ClearDelivered`，覆盖两种情况：

1. `ClaimDelivery` 判定 `duplicate` 时也会补写 dedup 标记（`sendOne` 里那段），可能为某些用户留下标记。
2. 多渠道场景下同一用户部分渠道成功、部分失败，成功渠道会留标记。

清理范围是 `inFailedSubs ∪ extraUsers` 笛卡尔积活动全部渠道，逐 key `DEL`，没有批量优化。用户数大时这里是 O(users × channels) 次 Redis 往返（同步执行在 HTTP 请求里），**大活动重推接口可能明显变慢**（未实测，属实现推断）。

---

## 6. 最硬的限制：流水唯一键

`push_records` 上有唯一键 `uk_task_user_channel(main_task_id, user_id, channel)`。重推时 `Gateway.sendOne` 调用 `ClaimDelivery`：

| 已有流水状态 | 结果 | 能否重发 |
|--------------|------|----------|
| `failed` / `cancelled` / `queued` | reclaim 成功，改回 `sending` | ✅ 能 |
| 陈旧 `sending`（`updated_at` 超 2 分钟） | 同上 | ✅ 能 |
| `sending`（2 分钟内） | `inFlight=true` | 稍后重试 |
| `sent` / `delivered` / `clicked` | `duplicate=true`，直接跳过 | ❌ 不能 |

也就是说：**渠道返回成功、但业务侧确认用户其实没收到**的场景，重推无效（`DeliveredOK()` 判定为已投递）。要重发只能新建一个活动（新的 `main_task_id`，唯一键不冲突）。

## 7. 边界与坑清单

| # | 事实 | 影响 |
|---|------|------|
| 1 | 仅 `failed`/`partial` 可重推 | `running` 中的活动想补发只能等终态。README 早期版本提到「代码也接受 running」，当前 `ReopenMainTask` 与 `IsRetryable` 都已排除 |
| 2 | 新分片不带 `vars`/`channels` | 个性化变量丢失，占位符可能外露；渠道求交失效 |
| 3 | `retry_user_count` 是估算 | 含失败分片里其实已成功的用户 |
| 4 | `ClearDelivered` 逐 key 同步删除 | 大活动重推接口耗时随用户×渠道增长 |
| 5 | `DeliveredOK` + 唯一键 | 「假成功」用户无法重推 |
| 6 | 重推不校验时间间隔、不限次数 | 无防抖，接口无鉴权，可被反复调用 |
| 7 | `resetN==0 && newSubs==0` 才报 40004 | 只要有失败分片就算「有内容可重推」，即使这些用户实际都成功了 |

## 8. 跟读与验证

```bash
# 1) 构造失败：创建活动时 payload 带 force_fail（stub 发送器识别）
curl -X POST localhost:8080/api/v1/campaigns -H 'Content-Type: application/json' -d '{
  "biz_id":"retry-demo-1","biz_scene":"demo","title":"t","channel":"inbox",
  "template_id":"tpl_welcome","audience_ref":"u1","audience_extra":{"total":5},
  "payload":{"force_fail":"permanent"}
}'

# 2) 等终态后查失败流水
# SELECT user_id,status,error_msg FROM push_records WHERE main_task_id=?;

# 3) 重推
curl -X POST localhost:8080/api/v1/campaigns/<id>/retry

# 4) 观察 sub_tasks.retry_count 递增、Redis sub_finished 被清空
redis-cli SMEMBERS starlink:task:<id>:sub_finished
```

`stub` 发送器支持 `payload.force_fail = retryable | permanent`（见 [`internal/adapter/channel/registry.go`](../internal/adapter/channel/registry.go)），是构造失败样本最省事的方式。
