# 单渠道 / 顺序降级 / 多渠道并行 · 精读

本文说明活动级多渠道策略（`single` / `fallback` / `parallel`）从创建归一化、落库快照、MQ 携带，到 Pusher `Gateway` 执行的完整链路。配套见 [`Pusher层代码解析.md`](Pusher层代码解析.md)。

---

## 1. 三种模式一句话

| 模式 | 语义 | 用户成功条件 | 典型用法 |
|------|------|--------------|----------|
| `single` | 只打一条渠道 | 该渠道发送成功 | `channel: "sms"` |
| `fallback` | **按 `channels` 数组顺序**依次尝试，成功即停 | 任一渠道成功 | App 推失败再短信 |
| `parallel` | 同内容多渠道 **同时**发 | 任一渠道成功 | App + 站内信双触达 |

共同点：

- 配置挂在 **活动（主任务）** 上，不是用户级、不是全局默认覆盖。
- 正文先 `RenderTemplate` **一次**，三种模式共用同一 `content`。
- 真正打渠道都走 `sendOne`：按 `(main_task, user, channel)` **独立去重 + 独立流水**。

## 2. 端到端位置

```text
POST /campaigns
  channel / channels / channel_mode
        │
        ▼
  NormalizeChannels()  → primary + 有序链 + 有效 mode
        │
        ▼
  main_tasks.channel / channels(JSON) / channel_mode
        │
        ▼
  Scheduler 组装 PushMessage
  Channels / ChannelMode / Channel（主渠道）
        │
        ▼
  Gateway.Handle
  EffectiveChannels() + EffectiveMode()
        │
        ├─ parallel  → sendParallel
        ├─ fallback  → sendFallback
        └─ default   → sendOne(chs[0])   // single
```

## 3. 创建时归一化（定规则的地方）

文件：[`internal/domain/message.go`](../internal/domain/message.go) `CreateCampaignInput.NormalizeChannels`

### 3.1 入参

| 字段 | 含义 |
|------|------|
| `channel` | 单主渠道；与 `channels` 二选一，或同时传（**`channels` 优先**） |
| `channels` | **有序**渠道链；fallback 的降级顺序、parallel 的并行列表都看它 |
| `channel_mode` | `single` \| `fallback` \| `parallel`；空 → Normalize 为 `single` |

### 3.2 算法

```text
1. 收集渠道：
   - 有 channels → 按数组顺序去重追加
   - 否则用 channel 单元素
   - 都空 → error
2. 非法 channel / mode → error
3. 纠偏 mode：
   - len(chs)==1 → 强制 single
   - len(chs)>1 且 mode==single（含默认空）→ 升为 fallback
4. 返回 (chs[0], chs, mode)
```

### 3.3 纠偏表（精读必记）

| 你传的 | 落库实际 |
|--------|----------|
| `channel: app_push`，不传 mode | `single` + 单渠道 |
| `channels: [app, sms]`，不传 mode 或 `single` | **`fallback`**（不是 single） |
| `channels: [app, sms], channel_mode: parallel` | `parallel` |
| `channels: [app, sms, app]` | 去重后 `[app, sms]`，顺序保留首次出现 |

设计意图：多渠道却写 `single` 没有可执行语义，自动当成「按序降级」更安全。

创建服务：[`campaign.Service.Create`](../internal/app/campaign/service.go) 调 `NormalizeChannels` 后写入：

- `Channel` = 链首（兼容旧字段 / 取消时 markCancelled 默认渠道）
- `Channels` = JSON 数组字符串
- `ChannelMode` = 纠偏后的 mode

## 4. 运行时再解析（防漂移）

落库后到执行还有两处「有效模式」计算，逻辑与创建纠偏一致：

| 位置 | 方法 |
|------|------|
| 主任务 | `MainTask.EffectiveChannelMode()` + `ChannelList()` |
| MQ 消息 | `PushMessage.EffectiveChannels()` + `EffectiveMode()` |

```go
// 伪代码共性
chs := Channels 优先，否则 [Channel]
if len(chs) <= 1 { return single }
if mode == single { return fallback }
return mode
```

Scheduler 写入消息时用的是主任务快照：

```go
Channels:    main.ChannelList()
ChannelMode: main.EffectiveChannelMode()
Channel:     main.Channel
```

之后改模板中心或其它活动不影响本活动；**本活动渠道策略创建后也不再改**（无 PATCH 渠道 API）。

## 5. Gateway 分发

[`Gateway.Handle`](../internal/push/gateway.go)：

```go
content := RenderTemplate(msg.Body, msg.Vars)
chs := msg.EffectiveChannels()
mode := msg.EffectiveMode()

switch mode {
case parallel:  return sendParallel(...)
case fallback:  return sendFallback(...)
default:        return sendOne(chs[0])  // single
}
```

去重/频控通过后，每个实际发送的渠道各自 `waitToken(channel, priority)`；超时返回 `ErrChannelThrottled` 留 PEL。

## 6. `single`：单渠道

```text
sendOne(ctx, msg, chs[0], content, save=true)
  ok  → Handle nil → MQ ACK
  !ok → 返回 err → 不 ACK
```

- 只认 `chs[0]`（通常等于 `msg.Channel`）。
- 不去尝试链上其它渠道（单元素链也无所谓）。
- 去重键：`(main, user, chs[0])`。

适用：明确只要短信 / 只要站内信，失败即失败（可依赖 MQ 重投 / 失败重推，而不是换渠道）。

## 7. `fallback`：按顺序降级

```155:194:internal/push/gateway.go
// sendFallback：前一渠道失败才试下一渠道，成功即停
```

### 7.1 控制流

```text
for i, ch := range chs:          // 顺序 = 创建时 channels 顺序
  cancelled → markCancelled(当前 ch) → return nil (ACK)
  paused    → return error (不 ACK)
  i>0       → waitToken
  ok, err = sendOne(ch)
  ok        → return nil          // 成功即停，后面渠道不碰
  err==nil  → return nil          // 取消路径等
  paused 错误 → return
  否则 lastErr，打日志试下一个
全挂 → return lastErr
```

### 7.2 语义细节

| 点 | 行为 |
|----|------|
| 顺序 | **严格按 `channels` 下标**，不是按渠道类型枚举 |
| 成功即停 | 第 1 渠道成功则第 2、3 不会 Claim、不会发 |
| 失败才降级 | `sendOne` 返回 `(false, err)` 才继续 |
| 去重跳过 | Redis/DB 已成功 → `(true,nil)` → 整用户成功，**不会**再降级 |
| 流水 | 每个尝试过的渠道各有一条 `push_records`；失败渠道留 `failed`，成功渠道 `sent` |
| 限流 | 每个实际尝试的渠道各扣 1 次该渠道配额 |

### 7.3 时序例

`channels: [app_push, sms, inbox]`

```text
app_push fail  → 流水 failed
sms      ok    → 流水 sent，MarkDelivered(sms)
inbox          → 不执行
Handle return nil → ACK
```

若三者都 fail → Handle error → 不 ACK（PEL 语义见 Pusher 精读）。

## 8. `parallel`：多渠道并行

```196:233:internal/push/gateway.go
// sendParallel：每渠道一个 goroutine，任一 ok 即用户成功
```

### 8.1 控制流

```text
for each ch in chs:
  go:
    waitToken
    sendOne(ch) → outcome{ok, err}
wait 全部结束
anyOK → return nil
else  → return lastErr / "all parallel channels failed"
```

### 8.2 与 fallback 的关键差异

| 维度 | fallback | parallel |
|------|----------|----------|
| 执行 | 串行，成功短路 | **全部启动**，无短路取消 |
| 成功定义 | 第一个成功的渠道 | 至少一个成功 |
| 失败流水 | 仅尝试过的渠道 | **每个渠道都会 Claim/发送**（除非本 goroutine 内取消） |
| 触达效果 | 通常一用户一渠道成功触达 | 可多渠道同时触达（重复打扰风险） |
| 限流 | 实际尝试次数 | ≈ 渠道数（各扣本渠道配额） |
| paused | 循环中立刻返回 | 各 goroutine 各自判断；整体仍等齐 |

### 8.3 精读坑

1. **没有 context 取消兄弟 goroutine**：一个成功不会打断其它渠道的 `Send`；其它可能仍写 `sent`/`failed`。
2. **用户成功 ≠ 全渠道成功**：`anyOK` 即 ACK；失败渠道流水仍在，失败重推逻辑按「用户是否有任一成功渠道」过滤（`ListFailedUserIDs`）。
3. **去重按渠道**：用户 A 的 app 成功、sms 失败；重投时 app 走 dedup skip，sms 可再试（若业务再次 parallel 投递）。

## 9. 公共底座：`sendOne`（三种模式都依赖）

每种模式最终都是对「单渠道一次投递」的组合。

```text
HasDelivered(Redis) 命中 → (true, nil)
ClaimDelivery(DB)
  duplicate → MarkDelivered → (true, nil)
  inFlight  → (false, err)
  占位成功 → doSend
    渠道 SPI Send + max_retry
    成功 → UpdateRecord(sent) + MarkDelivered
    失败 → UpdateRecord(failed)
    paused → 流水改 queued，(false, paused)
    cancelled → 流水 cancelled，(false, nil)
```

| 返回 | 上层策略怎么用 |
|------|----------------|
| `(true, _)` | fallback/parallel 计成功；single Handle 成功 |
| `(false, nil)` | 多为取消；fallback **停止整条链**（return nil）；parallel 不计 ok |
| `(false, err)` | fallback 试下一个；parallel 记 lastErr；single 失败 |

**去重维度含 channel**：fallback 里 app 失败再 sms，是两条独立占位，不会因为 app 失败而挡住 sms。

`SendRequest.MsgID` = `{msg.MsgID}-{channel}`，渠道侧可按渠道幂等。

## 10. 「用户成功」在三层系统的含义

| 层级 | single | fallback | parallel |
|------|--------|----------|----------|
| Gateway / ACK | 该渠道 ok | 链上任一 ok | 任一渠道 ok |
| `push_records` | 1 条主路径流水 | 1～N 条（失败+成功） | 通常 N 条 |
| Scheduler 主任务 success | **入队成功**口径，与渠道模式无关 | 同左 | 同左 |

排障「这个用户到底走了哪条渠道」：查 `push_records WHERE main_task_id=? AND user_id=?`，看各 `channel` 的 `status`。

## 12. 取消 / 暂停在各模式下的表现

| 事件 | single | fallback | parallel |
|------|--------|----------|----------|
| 发送前 cancelled | markCancelled(主渠道) ACK | 当前循环渠道 markCancelled ACK | Handle 入口已拦 |
| 发送中 cancelled | 该渠道流水 cancelled，`(false,nil)` | 若 err==nil 则整链停并 ACK | 各 goroutine 各自 cancelled；若皆非 ok 且无 err，可能走「all failed」 |
| paused | 不 ACK；流水可回 queued | 立即不 ACK，**不**试下一渠道 | 失败 goroutine 带 paused err；若另有渠道已 ok 仍整体 ACK |

paused + parallel 边界：一渠道已成功、另一渠道因 pause 失败 → `anyOK=true` → 仍 ACK（用户已触达）。

## 13. 如何选模式（产品视角）

| 诉求 | 选 |
|------|----|
| 只要一种触达，失败算失败 | `single` |
| 优先便宜/体验好的渠道，失败再换 | `fallback`，把首选放 `channels[0]` |
| 必须多端同时触达（强提醒） | `parallel`（接受重复打扰与更高 QPS） |
| 多渠道但漏写 mode | 系统当 `fallback` |

## 14. 建议断点阅读顺序

| 顺序 | 位置 | 看什么 |
|------|------|--------|
| 1 | `domain/status.go` ChannelMode | 三枚举定义 |
| 2 | `NormalizeChannels` | 创建纠偏 |
| 3 | `MainTask.EffectiveChannelMode` / `PushMessage.EffectiveMode` | 运行时一致 |
| 4 | `scheduler/worker.go` 组 PushMessage | 快照进 MQ |
| 5 | `Gateway.Handle` switch | 分发 |
| 6 | `sendFallback` / `sendParallel` | 短路 vs 全开 |
| 7 | `sendOne` / `ClaimDelivery` | 按渠道去重 |
| 8 | `ListFailedUserIDs` | 「用户维度失败」含多渠道 |

本地验证建议：同一用户建 fallback 活动，stub 第一渠道故意失败，看是否只第二渠道 `sent`；parallel 则两条都应有流水。
