## 2. 系统在做什么

一次「活动」= 一批用户 × 一个模板 × 一条或多条渠道。系统把这件事拆成三段异步流水线：

```text
业务方 ──HTTP──► API ──MySQL(main_tasks pending)──►
                            │
                   Scheduler │ 圈人 → 分片 sub_tasks → 每用户一条 PushMessage
                            ▼
                   MQ（high / normal 两条队列，驱动可换）
                            │
                     Pusher │ 渲染 → 限流 → 去重占位 → 调渠道 → 写 push_records
                            ▼
                   渠道厂商 ──回执──► POST /api/v1/callbacks/receipt
```

三个进程共用同一套 `internal`，靠配置和入口区分角色：

| 进程 | 入口 | 循环 | 关键依赖 |
|------|------|------|----------|
| API | [`cmd/api/main.go`](../cmd/api/main.go) | Gin HTTP | MySQL、Redis（重推清 dedup）、Limiter（创建准入） |
| Scheduler | [`cmd/scheduler/main.go`](../cmd/scheduler/main.go) | `loopSplit` + N×`loopClaim` | MySQL、Redis（聚合计数）、MQ 写、Audience |
| Pusher | [`cmd/pusher/main.go`](../cmd/pusher/main.go) | 每条队列一个 `Consumer` | MQ 读、MySQL（流水）、Redis（去重/配额/频控）、Channel |

## 3. 分层与依赖方向

```text
cmd/                 进程入口：解析 flag → bootstrap → 组装 service/worker → 优雅退出
 └── internal/bootstrap    唯一的「装配点」：Config → DB/Redis/MQ/Registry/Limiter
      ├── internal/server        路由表（Gin）
      ├── internal/handler       HTTP 出入参解包，无业务逻辑
      ├── internal/app/*         应用服务：campaign / template / callback
      ├── internal/scheduler     拆分、认领投递、终态聚合
      ├── internal/push          消费、推送网关、模板渲染
      ├── internal/port          全部可替换接口（SPI + 仓储）★依赖倒置的腰部
      ├── internal/domain        领域模型、状态机、入参校验、纯函数
      └── internal/adapter/*     MySQL / Redis / MQ / 人群 / 渠道 / Webhook 实现
pkg/                 errcode、response（与业务无关的通用件）
```

两条规则贯穿全仓：

1. **业务只依赖 `internal/port`**。`scheduler`、`push`、`app` 都不 import 具体 adapter（唯一例外：`campaign.Service` 直接持有 `*webhook.Client`，因为要用它的 `ResolveURL` / `NotifyAsync`；`scheduler.Splitter` 用自定义的 `AudienceResolver` 小接口反向解耦）。
2. **纯逻辑下沉到 `domain`**。渠道归一化、优先级映射、时窗判断、租约过期、状态可迁移性都是无副作用函数，所以单测能覆盖到（见 `internal/domain/*_test.go`）。

## 4. 依赖装配：`bootstrap.NewInfra`

[`internal/bootstrap/bootstrap.go`](../internal/bootstrap/bootstrap.go) 是三个进程共用的装配函数，顺序值得记住：

| 步骤 | 做什么 | 注意 |
|------|--------|------|
| 1 | `config.Load(path)` → `applyDefaults()` | 所有默认值集中在 `applyDefaults`，YAML 缺项不报错 |
| 2 | `repo.NewDB` + `repo.AutoMigrate` | **三个进程都会跑 DDL**；迁移前还有一条清理重复流水的原始 `DELETE`，其错误被 `_ =` 忽略 |
| 3 | `redisx.New` | 仅建客户端，不 Ping（Ping 在 scheduler/pusher 的 main 里） |
| 4 | `mq.TryInitRocketTransport`（仅 driver=rocketmq）→ `mq.Open` | 驱动按名字查注册表，见文档 07 |
| 5 | `channel.RegisterDefaults` → `channel.RegisterFromConfig` | 后注册覆盖先注册，所以 HTTP 发送器能盖掉 stub |
| 6 | 人群：HTTP Provider **先**注册，Demo Provider 后注册 | `Registry.Resolve` 取第一个 `Supports` 命中的 Provider，顺序决定优先级 |
| 7 | 挂 4 个 Filter：合规 → 黑名单 → 退订 → AB | 顺序即执行顺序 |
| 8 | `webhook.New`、`redisx.NewChannelQuotaLimiter` | Limiter 在 `enabled=false` 时退化为进程内全局桶 |

返回的 `Infra` 是个「什么都有」的结构体，各 `main` 只挑自己需要的字段，所以 API 进程也持有 MQ（未使用）。

## 6. 全局约定速查

| 约定 | 位置 | 说明 |
|------|------|------|
| 统一响应体 | [`pkg/response`](../pkg/response/response.go) | `{code,message,data}`；`Fail` 对非 `*errcode.Error` 直接回显 `err.Error()` |
| 错误码 | [`pkg/errcode`](../pkg/errcode/errcode.go) | `40901/40902/40903` → HTTP 409；`>=50000` → 500；其余 4xxxx → **400** |
| 日志 | 标准库 `log/slog` | 关键路径带 `stage` 字段（`admission_reject`、`enqueue_slowdown`、`quota_timeout`、`split_over_capacity`） |
| 幂等键 | `main_tasks.biz_id` 唯一索引 | 创建活动幂等，见 01 |
| 投递唯一键 | `push_records(main_task_id,user_id,channel)` | 最终防重，见 09 |
| 可延后重投的 sentinel 错误 | [`internal/domain/errors.go`](../internal/domain/errors.go) | `ErrMainTaskPaused` / `ErrOutsideSendWindow` / `ErrQuietHours` / `ErrChannelThrottled`：留 PEL、不进 DLQ、不记业务失败 |
| 乐观锁 | `main_tasks.version`、`push_templates.version` | 仅终态切换 / 模板更新用 CAS，计数走原子递增 |
