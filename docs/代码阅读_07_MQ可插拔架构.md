## 1. 三个接口的分工

```go
type MessageQueue interface {          // 单个 topic + consumer group
    Publish(ctx, msgs []domain.PushMessage) error
    Consume(ctx, consumerID string, batch int, handler func(ctx, msg) error) error
    EnsureReady(ctx) error
}

type MessagePublisher interface { Publish(...) error }   // Scheduler 只要这个

type PriorityBroker interface {        // 双队列门面
    MessagePublisher
    Driver() string
    High() MessageQueue
    Normal() MessageQueue
    EnsureReady(ctx) error
    Close() error
}
```

`Consume` 的契约写在注释里，是实现驱动时必须遵守的约定：

> `batch` 同时表示预取批量与**最大并发 handler 数**；实现方应在受限 worker 内调用 handler，并在该 worker 内完成 ACK / 失败重试，不要在同步读循环里串行处理。

也就是说，并发度由驱动负责实现，`push.Consumer` 只是把 `worker_concurrency` 透传下去：

```go
// internal/push/consumer.go 全部逻辑
return c.mq.Consume(ctx, c.consumerID, c.concurrency, func(ctx, msg) error {
    return c.gateway.Handle(ctx, msg)
})
```

## 2. 注册表与装配

```go
type Deps struct {                     // 驱动能拿到的东西
    Cfg   config.MQConfig
    Redis *redis.Client                // 仅 redis_stream 需要
}
type Queues struct { High, Normal port.MessageQueue }
type Factory func(deps Deps) (*Queues, error)

func Register(name string, f Factory)  // 重复注册直接 panic
func Drivers() []string
func Open(deps Deps) (port.PriorityBroker, error)
```

三个内置驱动都在自己文件的 `init()` 里注册，所以 import 包即注册。`Open` 的流程：

```text
driver = cfg.Driver（空 → redis_stream）
查注册表 → 不存在则报错，错误信息里列出已注册驱动
f(deps) → 校验 High/Normal 都非 nil
NewPriorityRouter(driver, high, normal)
```

装配入口只有一处：[`bootstrap.NewInfra`](../internal/bootstrap/bootstrap.go)

```go
if cfg.MQ.Driver == "rocketmq" { mq.TryInitRocketTransport(cfg.MQ.RocketMQ) }
broker, err := mq.Open(mq.Deps{Cfg: cfg.MQ, Redis: rdb.RDB()})
slog.Info("mq ready", "driver", ..., "high", ..., "normal", ..., "drivers", mq.Drivers())
```

启动日志里的 `drivers` 字段能直接确认哪些驱动被编进了二进制（`rocketmq` 无论是否带 tag 都会出现，因为注册与 transport 注入是两件事）。

## 3. 队列命名的兼容层

```go
type MQQueueConfig struct {
    Topic  string   // 通用名（RocketMQ / Kafka）
    Stream string   // Redis Stream 名（旧字段）
    Group  string
}
func (q MQQueueConfig) TopicOrStream() string { if q.Topic != "" { return q.Topic }; return q.Stream }
```

`config.applyDefaults()` 里的兼容逻辑（[`internal/config/config.go`](../internal/config/config.go)）：

```text
normal 名为空 → 用顶层 mq.stream，否则 "starlink:push:normal"
normal group 为空 → 用顶层 mq.group，否则 "pushers-normal"
high 名/组为空   → "starlink:push:high" / "pushers-high"
最后回填顶层 mq.stream / mq.group = normal 的值（便于日志与旧代码读取）
```

结论：旧配置只写 `mq.stream`/`mq.group` 时，它被当作 **normal** 队列，high 用默认名。

## 4. `PriorityRouter`：驱动无关的分流

```go
func (r *PriorityRouter) Publish(ctx, msgs) error {
    分成 high / normal 两个切片（按 msg.Priority.IsHigh()）
    非空则分别调用对应队列的 Publish，错误包装成 "publish high/normal: %w"
}
func (r *PriorityRouter) Queue(p domain.Priority) port.MessageQueue  // 便利方法
func (r *PriorityRouter) EnsureReady(ctx) error                      // 两条都建
func (r *PriorityRouter) Close() error                               // 若驱动实现了 Close 则调用
```

它同时实现了 `PriorityBroker` 和 `MessageQueue`（编译期断言在文件末尾）。**这里有个陷阱**：

```go
func (r *PriorityRouter) Consume(ctx, consumerID, batch, handler) error {
    return r.normal.Consume(ctx, consumerID, batch, handler)   // ★ 只消费 normal
}
```

把 Router 当 `MessageQueue` 用会静默只消费普通队列。正确用法是 `pusher/main.go` 里那样显式取两条队列：

```go
runs = append(runs,
    queueRun{"high",   infra.MQ.High(),   cfg.Pusher.HighWorkerConcurrency},
    queueRun{"normal", infra.MQ.Normal(), cfg.Pusher.WorkerConcurrency},
)
// 每条队列一个 goroutine + 独立 consumerID（baseID + "-high"/"-normal"）
```

`-queue=high|normal|all` 就是在这里生效的，用于把事务流量和营销流量部署到不同实例。

`Publish` 的一个语义细节：分流是**逐条按消息的 Priority** 决定的，而不是按活动。理论上一个批次可以同时含两种优先级；实际上 Scheduler 组装一个子任务的消息时用的是同一个 `main.Priority`，所以每批只会落到一条队列。

## 5. 三个驱动的能力对照

| 能力 | redis_stream | memory | rocketmq |
|------|--------------|--------|----------|
| 需要外部组件 | Redis 5.0+ | 无 | NameServer/Proxy + `-tags rocketmq` |
| 并发 handler | ✅ worker 池（`batch`） | ✅ worker 池 | ⚠️ 仅限制在途数，实际取决于 SDK 回调是否并发 |
| 失败重投 | ✅ PEL + `XAUTOCLAIM` | ⚠️ 失败后重新塞回 channel（`default:` 满则**丢弃**） | 依赖 SDK 重试 |
| 死信 | ✅ `topic:dlq` | ❌ | ❌ |
| 容量治理 | ✅ `MAXLEN`/`XTRIM`/ACK 后 `XDEL` | 固定缓冲 `buffer_size` | 由 broker 负责 |
| 坏消息（反序列化失败） | 进 DLQ 后 ACK | 无处理（handler 不会被调用到坏数据，因为没有序列化） | **丢弃**（返回 nil，避免毒丸） |
| 适用场景 | 默认，生产可用 | 单测 / 无中间件联调 | 已有 RocketMQ 基建 |

### 5.1 MemoryQueue

```go
Publish: 逐条写 channel（ctx 可取消）；关闭后返回错误
Consume: sem(batch) 控制并发；handler 失败 → select { case q.ch <- m: default: }  // 队列满即丢
Close:   close(channel)，幂等
```

单测 `TestMemoryQueueConcurrentConsume` 验证了并发上限落在 `[2, concurrency]` 区间。

注意它的「重试」既没有次数上限也没有退避，失败消息会被立刻塞回队尾，可能出现忙循环；只适合测试。

### 5.2 RocketMQ：Transport 注入模式

官方 SDK 不进默认构建，抽象成接口：

```go
type RocketTransport interface {
    Start(ctx) error
    EnsureTopic(ctx, topic) error
    Send(ctx, topic string, body []byte) error
    Subscribe(ctx, topic, group, consumerID string, onMessage func(ctx, body []byte) error) error
    Close() error
}
func SetRocketTransport(t RocketTransport)   // 必须在 mq.Open 之前
```

`rocketmq_init.go` 留了一个可被 build tag 覆盖的钩子：

```go
var rocketInitFn = func(cfg config.RocketMQConfig) {}    // 默认空实现
func TryInitRocketTransport(cfg config.RocketMQConfig) { rocketInitFn(cfg) }
```

带 `-tags rocketmq` 编译时，`rocketmq_apache.go`（本仓已有该文件，147 行）在 `init` 中把真实实现挂到 `rocketInitFn`。未注入 Transport 时 `Open` 返回明确的报错，提示编译 tag 与配置项。

消费侧的 `sem` 只是在 `onMessage` 回调里占位再释放；如果 SDK 串行回调，并发度不会提升——注释里也写明了这点。

## 6. 自定义驱动（例如 Kafka）

```go
package mykafka

func init() {
    mq.Register("kafka", func(deps mq.Deps) (*mq.Queues, error) {
        high, err := newKafkaQueue(deps.Cfg.High.TopicOrStream(), deps.Cfg.High.Group)
        if err != nil { return nil, err }
        normal, err := newKafkaQueue(deps.Cfg.Normal.TopicOrStream(), deps.Cfg.Normal.Group)
        if err != nil { return nil, err }
        return &mq.Queues{High: high, Normal: normal}, nil
    })
}
```

然后 `driver: kafka`，并确保这个包被 import（通常在 `bootstrap` 或 `cmd` 里加空导入）。

实现 checklist：

1. `Consume` 必须自己起 worker 池并在 worker 内 ACK，否则 `worker_concurrency` 形同虚设。
2. 必须识别 [`domain/errors.go`](../internal/domain/errors.go) 的四个 sentinel 错误（paused / 时窗 / 免打扰 / 限流），把它们当作「稍后重投」而不是失败，也不要计入死信。
3. `EnsureReady` 里做 topic/group 的幂等创建。
4. 若持有连接，实现 `Close() error`（Router 会通过类型断言调用）。

## 7. 边界与坑清单

| # | 事实 | 影响 |
|---|------|------|
| 1 | `PriorityRouter.Consume` 只消费 normal | 误用会导致 high 队列无人消费且无报错 |
| 2 | `Register` 重复注册 panic | 自定义驱动名不要与内置重名 |
| 3 | memory / rocketmq 无 PEL/DLQ 等价物 | 换驱动等于放弃 Redis Stream 那套可靠性；memory 甚至会丢消息 |
| 4 | rocketmq 坏消息直接 ACK 丢弃 | 无死信留痕 |
| 5 | `Open` 失败时 bootstrap 直接返回错误 | 三个进程都会启动失败（快速失败，符合预期） |
| 6 | 只有 pusher 会 `MQ.Close()` | api/scheduler 退出时不关连接（进程退出即释放） |
| 7 | `batch` 一词三义 | 预取数量、`XREADGROUP COUNT`、并发 handler 数共用一个参数 |

## 8. 跟读与验证

```bash
# 看驱动是否按预期装配
docker compose logs pusher | grep 'mq ready'

# 两条 Stream 应分别有消息（redis_stream）
redis-cli XLEN starlink:push:high
redis-cli XLEN starlink:push:normal

# 只跑一条队列
go run ./cmd/pusher -config configs/config.yaml -queue=high
```

单测：`go test ./internal/adapter/mq/...`（覆盖 memory 并发、DLQ 命名、死信判定、容量选项换算）。

切 memory 驱动做端到端联调（无需 Redis Stream，但仍需 Redis 做去重/聚合）：

```yaml
mq:
  driver: memory
  memory: { buffer_size: 4096 }
```

注意 memory 是**进程内**队列，scheduler 与 pusher 必须在同一进程才能连通——当前 `cmd` 拆成三个进程，所以 memory 驱动实际只适合单测与自建 harness。
