## 1. 协程模型

```text
Worker.Run(ctx)
 ├── go loopSplit(ctx)                 // 1 条：每 poll_interval 一拍
 │      ├── splitPending()             // 最多 10 条到期 pending
 │      └── recoverStaleSplits()       // 最多 10 条租约过期卡单
 │            └── spawnSplit() → splitSem（split_concurrency，默认 2）→ go runSplit()
 └── go loopClaim(ctx, i) × worker_concurrency（默认 8）
        └── ClaimSubTask → processSubTask → Publish → UpdateSubTaskResult → OnSubFinished
```

worker 身份：`w.id = "scheduler-" + uuid[:8]`；认领时再拼协程下标 `fmt.Sprintf("%s-%d", w.id, idx)` 写入 `sub_tasks.worker_id`。**主任务租约用 `w.id`，子任务认领用 `w.id-idx`**，两者不同，别混。

水平扩展不需要选主：所有抢占都通过 MySQL 的条件更新 / 行锁完成，多起进程即可。

## 2. 拆分权抢占与租约

### 2.1 抢占 pending

```sql
UPDATE main_tasks
SET status='running', started_at=NOW(), split_owner=?, split_lease_at=NOW()
WHERE id=? AND status='pending';
```

`RowsAffected>0` 才拥有拆分权。抢到之后 `runSplit` 会**再读一次**主任务（`GetMainTask`），处理「抢占瞬间被取消/暂停」的窗口：

| 抢占后状态 | 动作 |
|------------|------|
| `cancelled` | 取消未完成子任务 + `ClearSplitLease`，不拆 |
| `paused` | `ClearSplitLease`，不拆 |
| 其他 | `DeleteSubTasksByMainTask`（清半成品）→ `Splitter.Split` |

### 2.2 租约三件套

| 机制 | 代码 | 说明 |
|------|------|------|
| 续约 | `RenewSplitLease(id, owner)`：`WHERE id=? AND status='running' AND split_owner=?` | 每翻一页人群续一次；返回 false 表示**丢租约**，立即中止拆分 |
| 清理 | `ClearSplitLease(id)` | 拆分成功收尾、或失败/取消/暂停退出时清空 `split_owner`/`split_lease_at` |
| 回收 | `ListStaleSplitMainTasks` + `ClaimStaleSplitMainTask` | 见下 |

**租约字段同时充当「拆分是否完成」的门闸**：`ClaimSubTask` 的 JOIN 条件里要求 `main_tasks.split_owner = '' OR IS NULL`，所以拆分未收尾时，已落库的分片不会被提前认领。这是流式拆分（边圈人边写子任务）能安全工作的前提。

### 2.3 卡单回收

```sql
-- 列出候选
SELECT * FROM main_tasks
WHERE status='running' AND split_owner <> '' AND split_owner IS NOT NULL
  AND (split_lease_at IS NULL OR split_lease_at < NOW() - INTERVAL lease SECOND)
ORDER BY id ASC LIMIT 10;
```

```go
// 抢占：事务内 SELECT ... FOR UPDATE 复核，再条件更新
ClaimStaleSplitMainTask:
  锁行 → 校验 status=running && split_owner!='' && 租约确实过期
       → UPDATE split_owner=me, split_lease_at=NOW(), sub_task_total=0, total_count=0
```

抢到后 `runSplit` 先删掉全部半成品子任务再全量重拆，因此不会重复分片。`sub_task_total`/`total_count` 归零也是为了重拆能重新累计。

`domain.SplitLeaseExpired(leaseAt, timeoutSec, now)` 是对应的纯函数（`nil` 租约视为过期），有单测 `TestSplitLeaseExpired`。

> 注意：候选条件只看「租约过期 + 仍持有 owner」，不再要求「无子任务」。所以流式拆分中途崩溃（已写了几个分片）也能被回收重拆。README 里旧版描述的「无子任务卡单」是更早的实现。

## 3. 流式拆分 `Splitter.Split`

每一页循环体的顺序（顺序即安全性）：

```text
1. GetMainTask 复核：cancelled → 取消子任务并报错；paused → 报错
2. RenewSplitLease：丢租约 → 报错退出
3. audience.Resolve(pageToken, PageSize=batch_size)
4. 空页且 !HasMore → break
5. 过滤/抽样/渠道求交 → ids/varMap/chMap
6. 本页非空 → CreateSubTasks（1 个分片）→ shard++、total += n、wroteAny=true
7. PatchMainMeta(id, total, 0)   ← 只写 total_count，sub_task_total 保持 0
8. !HasMore → break，否则 pageToken = NextPageToken
```

收尾：

```text
wroteAny==false → errcode.AudienceEmpty（→ 主任务 failed）
GetMainTask 复核 cancelled
UpdateMainTaskStats(..., status=running)     // 把 pending/running 推到 running
PatchMainMeta(id, total, shard)              // ★ 此刻写入 sub_task_total
ClearSplitLease(id)                          // ★ 放开 ClaimSubTask
checkOverCapacity(...)                       // 配额告警/自动暂停
```

`PatchMainMeta` 的 WHERE 明确排除 `cancelled/paused/终态`，所以不会把已暂停的活动数据写回去，也不碰 `status`：

```sql
UPDATE main_tasks SET total_count=?, sub_task_total=?
WHERE id=? AND status NOT IN ('cancelled','paused','success','partial','failed');
```

「先写 total、最后写 sub_task_total」的用意是：聚合器判定终态需要 `sub_task_total>0 && done>=sub_task_total`，若拆分中途就写入部分总量，可能在还没拆完时误判终态。

## 4. 子任务认领：`ClaimSubTask`

```sql
SELECT sub_tasks.* FROM sub_tasks
JOIN main_tasks ON main_tasks.id = sub_tasks.main_task_id
     AND main_tasks.status = 'running'
     AND (main_tasks.split_owner = '' OR main_tasks.split_owner IS NULL)
WHERE sub_tasks.status IN ('pending','retrying')
   OR (sub_tasks.status='running' AND sub_tasks.claimed_at IS NOT NULL
       AND sub_tasks.claimed_at < NOW() - INTERVAL claim_timeout_sec SECOND)
ORDER BY sub_tasks.id ASC
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

随后在同一事务里做条件更新：

```sql
UPDATE sub_tasks SET status='running', worker_id=?, claimed_at=NOW(), started_at=NOW()
WHERE id=? AND status IN ('pending','retrying','running');
```

`RowsAffected=0` → 返回 `gorm.ErrRecordNotFound` → 上层视为「没抢到」（`claimed=nil`，不是错误）。

四层保护叠在一起：

| 保护 | 作用 |
|------|------|
| `SKIP LOCKED` | 多实例并发认领不互相阻塞（要求 MySQL 8.0） |
| JOIN 主任务 `status=running` | 已取消/暂停/终态的活动，其子任务不会被认领 |
| JOIN `split_owner` 为空 | 拆分未收尾不认领 |
| `claimed_at` 超时条件 | 认领者崩溃后，`claim_timeout_sec`（默认 60s）之后可被接管 |

## 5. 丢认领保护：`UpdateSubTaskResult`

超时接管带来一个经典竞态：原 worker 复活后也会写结果，导致同一子任务被计入两次。解法是在写结果时校验认领人：

```sql
UPDATE sub_tasks SET success_count=?, fail_count=?, status=?, last_error=?, finished_at=NOW()
WHERE id=? AND worker_id=? AND status IN ('running','retrying');
```

返回 `updated bool`。调用方（`processSubTask` 成功路径、`loopClaim` 失败路径）都遵守同一约定：

```go
if !updated {
    slog.Info("skip success/fail aggregate: lost claim", ...)
    return / continue          // ★ 不调用 OnSubFinished
}
_ = w.agg.OnSubFinished(...)
```

**丢认领就不聚合**，避免虚高 `sub_task_done`。

## 6. 聚合幂等：Redis SET

即使有上面的保护，仍可能出现重复调用（比如进程重启后的重放）。`Aggregator.OnSubFinished` 再加一道按子任务 ID 的幂等：

```go
first, _ := cache.TryMarkSubFinished(mainTaskID, subTaskID)   // SADD starlink:task:{id}:sub_finished
if !first { return nil }                                      // 重复，直接跳过
done, _ := cache.IncrSubDone(mainTaskID, success, fail)        // HINCRBY stats
```

`SAdd` 返回 1 才是首次；首次时顺带 `EXPIRE 7d`。重推时 `SetSubDone` 会 `DEL` 这个 SET，让被重置的分片可以再次计入（见文档 03）。

单测 `TestOnSubFinishedIdempotent`（[`internal/scheduler/aggregator_test.go`](../internal/scheduler/aggregator_test.go)）固化了这个行为。

## 7. `processSubTask`：门禁与消息组装

```text
1. GetMainTask 门禁：cancelled → 子任务标 cancelled，返回 errMainCancelled（loopClaim 静默 continue）
                     paused    → ReleaseSubTask 放回 pending，返回 errMainPaused
2. 解析 user_ids / vars / channels
3. 解析 main.Payload → extra（透传给 SendRequest.Extra）
4. 组装 []PushMessage：
     MsgID = "<main>-<sub>-<user>"
     渠道：payload.channels[uid] 优先，否则任务链；单渠道时 mode 强制 single
     Body = main.TemplateBody（快照），Vars = payload.vars[uid]
     Priority = main.Priority.Normalize()
5. ★ 再 GetMainTask 一次，重复门禁（组装可能耗时）
6. publishMsgs(main, msgs)
7. UpdateSubTaskResult(success=len(msgs), fail=0, status=success)
8. updated → OnSubFinished(len(msgs), 0)
```

失败路径在 `loopClaim` 里统一处理：`UpdateSubTaskResult(0, st.TotalCount, failed, err)` + `OnSubFinished(0, TotalCount)`。

注意第 7 步的语义：**成功数 = 入队条数**，不是发送成功数。渠道求交被跳过的用户既不计成功也不计失败（`len(msgs) < st.TotalCount` 时差额被静默吞掉），这会让流水线口径的成功数小于子任务 `total_count`。

`ReleaseSubTask` 只在 `status='running'` 时生效，把 `worker_id/claimed_at/started_at` 清空并写 `last_error='released due to pause'`。

## 8. 入队节奏与反压（简述）

`publishMsgs` 有两条路径：

```text
pace = main.PaceQPS
若 limiter 启用且 SustainedHigh(channel, prio, util)：
    pace<=0 → pace = backpressure.default_pace_when_throttled（默认 50）
    pace>0  → pace = pace * slowdown_factor（默认 0.3，最小 1）
    日志 stage=enqueue_slowdown

pace>0 → 逐条 Publish，间隔 time.Second/pace（下限 1ms）
pace<=0 → 一次性批量 Publish
```

代价：`pace>0` 时是**逐条**发布，Redis 管道优势消失，且这个 goroutine 会被 `time.After` 占住。反压细节见文档 10。

## 9. 边界与坑清单

| # | 事实 | 影响 |
|---|------|------|
| 1 | 每拍 `splitPending` 与 `recoverStaleSplits` 各限 10 条 | 拆分吞吐上限 = 10 / poll_interval，且受 `split_concurrency` 限制 |
| 2 | `ClaimSubTask` 每次只取 1 条 | 每条子任务一个事务 + 一次 SELECT，QPS 高时 DB 压力集中在这条 SQL |
| 3 | 认领循环空转时 `time.Sleep(poll_interval)` | 无空闲退避策略，恒定 500ms 轮询 |
| 4 | 渠道求交跳过的用户不计入成功/失败 | 流水线计数与 `total_count` 不等 |
| 5 | 拆分失败 → 主任务 `failed`，但半成品分片保留 | 依赖租约回收重拆；若此时被人 `retry`，`ResetFailedSubTasks` 只重置 failed 子任务（半成品是 pending，不受影响） |
| 6 | `errMainPaused` 路径不重试计数 | 暂停期间子任务反复被认领/释放，`loopClaim` 会持续空转（有 `poll_interval` 兜底） |
| 7 | `spawnSplit` 用 `ctx` 而非子 ctx | 进程退出时拆分被直接取消，半成品留给下次租约回收 |
| 8 | `sub_tasks.user_ids` 单行存整页用户 | `batch_size` 过大时单行膨胀（`mediumtext` 上限 16MB） |

## 10. 跟读与验证

```sql
-- 拆分进行中（租约仍在）
SELECT id, status, split_owner, split_lease_at, total_count, sub_task_total
FROM main_tasks WHERE status='running';

-- 被认领但迟迟未完成的分片
SELECT id, main_task_id, worker_id, claimed_at, retry_count, status
FROM sub_tasks WHERE status='running' AND claimed_at < NOW() - INTERVAL 1 MINUTE;
```

日志关键词：`main task split done`、`reclaim stale split main task`、`cleared partial subtasks before split`、`skip success aggregate: lost claim`、`main task aggregated`。

制造卡单实验：拆分中途 `kill -9` scheduler，等 `split_lease_sec`（默认 90s）后重启，应看到 `reclaim stale split main task` 与半成品清理日志。
