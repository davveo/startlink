## 1. 契约：三个结构体

```go
type AudienceQuery struct {                 // 平台 → 业务
    AudienceRef string          // 活动里的人群引用；静态段 = segment code
    BizScene    string          // 路由依据；静态锁定 "static"
    Extra       map[string]any  // 活动的 audience_extra 原样透传
    PageToken   string
    PageSize    int
}

type AudiencePage struct {
    Users         []TargetUser
    NextPageToken string
    TotalHint     int64
    HasMore       bool           // ★ 翻页终止条件看这个
}

type TargetUser struct {
    UserID   string
    Channels []ChannelType
    Vars     map[string]string
    Extra    map[string]any      // AB：ab_keep；静态：phone / email
}
```

翻页由 `HasMore` 驱动。`Extra.phone` / `Extra.email` 经拆分写入子任务 `extras`，Worker 合并进 `PushMessage.Extra`，Gateway 填入 `SendRequest.Extra`，供短信/邮件 Sender 取号。

## 2. 路由：`Registry.Resolve`

```go
for _, p := range r.providers {
    if p.Supports(query.BizScene) { provider = p; break }   // ★ 先注册先命中
}
if provider == nil { return errcode.UnsupportedScene }       // 40003
page, err := provider.Resolve(ctx, query)
for _, f := range r.filters { users, err = f.Filter(ctx, bizScene, users) }  // 链式
page.Users = users
```

两个设计点：

- **顺序即优先级**。`bootstrap` 里注册顺序为 **Static → HTTP → Demo**：Static 只认 `biz_scene=static`，不会抢业务场景；HTTP 优先于 Demo，避免 Demo 截胡。
- **过滤在 Provider 之后统一执行**，业务侧只管圈人，黑名单/退订/合规交给平台 Filter；**发送期** Gateway 再做偏好/退订终检（见 §4.1）。
- 整个 `Resolve` 持 `RLock`，Provider 的网络请求也在锁内——只影响 `Register`（启动期一次性），运行期无竞争。

`Splitter` 并不直接依赖 `*audience.Registry`，而是声明了一个只有 `Resolve` 的小接口 `AudienceResolver`，方便替换与测试。

## 3. 内置 Provider

### 3.1 DemoProvider（联调假人群）

| 项 | 行为 |
|----|------|
| 支持场景 | 仅 `audience.demo_scenes`（默认 `demo`、`dev`），大小写不敏感、trim |
| 总量 | 读 `Extra["total"]`（float64 或 int），默认 500 |
| 分页 | `PageToken` 就是偏移量的十进制字符串 |
| 用户 ID | `u_<audience_ref>_<n>`，n 从 1 开始 |
| 变量 | `name=User<n>`、`score=<n>` |
| 可达渠道 | **每第 4 个用户**（`(i+1)%4==0`）只可达 `inbox`，其余为空（沿用任务渠道） |

那条 `%4` 规则是刻意留的坑位样本：用它能直接验证 `IntersectChannels` 的行为——比如活动只发 `sms` 时，这批用户会被整个跳过。

早期版本的 Demo Provider 会兜底所有 `biz_scene`，现在必须命中 `demo_scenes`，否则 `40003`。生产建议 `demo_enabled: false`。

### 3.2 HTTPProvider（真实圈人）

```yaml
audience:
  demo_enabled: false
  http:
    enabled: true
    url: "https://your-audience/resolve"
    scenes: [marketing, payment]   # 空 = 承接所有非空 biz_scene
    timeout_sec: 10
```

- `POST url`，body 是 `AudienceQuery` JSON，响应必须是 `AudiencePage` JSON。
- `Supports`：`url` 为空一律 false；`scenes` 为空 → `acceptAll`（任何非空 scene 都接）；否则精确匹配（小写 trim）。
- 状态码 `>=300` → 报错，错误信息截断 200 字符；`Splitter` 会把它变成拆分失败 → 主任务 `failed`。
- 超时是 `http.Client.Timeout`，同时 `ctx` 也会传下去（`NewRequestWithContext`）。
- 无签名、无重试、无熔断。单页失败即整个活动拆分失败（会保留半成品子任务，等租约过期后重拆，见文档 06）。

### 3.3 StaticProvider（CSV / JSON 静态名单）

| 项 | 行为 |
|----|------|
| 支持场景 | 仅 `biz_scene=static`（常量 `domain.BizSceneStatic`） |
| `audience_ref` | 人群段 `code` |
| 数据 | 表 `audience_segment_members`（`user_id` + `phone`/`email` + 可选 vars） |
| 分页 | `PageToken` = 行 offset；`TotalHint` = COUNT |
| Extra | 有值则写 `phone` / `email`，供短信/邮件 Sender 使用 |

创建 `source=static` 的人群段时，服务端锁定 `biz_scene=static`、`audience_ref=<code>`。活动传 `segment_code` 展开时也会**强制** `BizScene=static`，避免运营台仍带 `demo` 场景时被 DemoProvider 截胡。

导入 API：`POST /api/v1/segments/:code/members/import`（JSON 或 multipart CSV）。表头认 `phone`/`email`/`user_id`（及中文别名）。无 `user_id` 时生成 `phone:…` / `email:…`。详见手册 §9.5。

## 3.4 人群段资产（Segment）与排除名单

- **include 段**：创建活动填 `segment_code` → `campaign.applySegments` 回填 `audience_ref` / `audience_extra`（活动 extra 覆盖段参数）；静态段另强制 scene。
- **exclude 段**：`exclude_segment_code` 在拆分前由 `segment.Service.ResolveExcludeUserIDs` 一次展开，Splitter 逐用户剔除；停用或超限（页数/人数）→ **整单失败**。
- **抑制名单管理面**：黑名单/退订 DB 权威 + Redis 快路径，与 Filter 共用键；见手册 §10。

## 4. 四条过滤链（注册顺序 = 执行顺序）

| 顺序 | Filter | 依据 | 行为 |
|------|--------|------|------|
| 1 | `ComplianceFilter` | user_id 后缀 | 丢弃以 `_block` 结尾的用户（示例实现） |
| 2 | `BlacklistFilter` | Redis SET `compliance.blacklist_key` | `SIsMember` 命中则丢弃用户 |
| 3 | `UnsubscribeFilter` | Redis SET `unsubscribe_key_prefix + channel` | 从 `u.Channels` 里剔除退订渠道；**剔完为空则丢用户**；`u.Channels` 本来为空则原样保留 |
| 4 | `ABSampleFilter` | `u.Extra["ab_keep"]` | 显式 `false` 才丢；百分比抽样在 Splitter 里做 |

性能特征：`BlacklistFilter` / `UnsubscribeFilter` 多为逐用户 `SIsMember`，大规模时是热点。

### 4.1 发送期终检（补齐「Channels 为空」缺口）

`UnsubscribeFilter` 在用户未声明 `Channels` 时会放行——退订判断推迟到发送期。**Gateway 已实现终检**（旧文档写「Gateway 不再查」已过时）：

- Redis 渠道退订 + `UserPreference.Blocks()`（主题/营销/渠道偏好）
- 用户级免打扰与全局 `quiet_hours` 取并集（high 优先级不受约束）
- 营销频次 `freq.marketing_*`（仅 normal）

命中后写 `suppressed`（或对应状态）并 ACK，不进 DLQ。详见 Pusher 层与手册 §11。

## 5. Splitter 侧的二次加工

`Registry.Resolve` 返回后，[`Splitter.Split`](../internal/scheduler/splitter.go) 还会做三件事：

```go
abPercent := extra["ab_sample_percent"]      // -1 表示未配置
for _, u := range page.Users {
    if u.UserID == "" { continue }
    if abPercent >= 0 && !audience.SampleByPercent(u.UserID, abPercent) { continue }
    chs := domain.IntersectChannels(taskChs, u.Channels)
    if len(chs) == 0 { slog.Info("skip user: no reachable channel intersect"); continue }
    ids = append(ids, u.UserID)
    if len(u.Vars) > 0     { varMap[u.UserID] = u.Vars }
    if len(u.Channels) > 0 { chMap[u.UserID] = chs }     // 只有用户声明过渠道才写
}
```

### 5.1 AB 抽样

```go
func SampleByPercent(userID string, percent int) bool {
    if percent >= 100 { return true }
    if percent <= 0   { return false }     // ★ 0 = 全部丢弃
    h := fnv.New32a(); h.Write([]byte(userID))
    return int(h.Sum32()%100) < percent
}
```

稳定哈希，同一用户在多次拆分中结果一致。注意 `ab_sample_percent: 0` 会**圈不到任何人**，进而 `wroteAny=false` → `errcode.AudienceEmpty` → 主任务变 `failed`。

### 5.2 渠道求交 `IntersectChannels`

```text
taskChs 空            → nil
userChs 空            → 复制 taskChs（沿用任务渠道链）
否则                  → 保留 taskChs 中出现在 userChs 里的项，★保持任务链顺序
```

保持任务链顺序很关键：`fallback` 的降级次序由活动定义，不能被用户渠道列表的顺序改写。求交为空的用户直接被跳过（不计入 total，不产生流水）。

单测覆盖：`go test ./internal/domain -run TestIntersectChannels`。

### 5.3 子任务 payload 形态

```json
{
  "user_ids": ["u_1","u_2"],
  "vars":     {"u_1": {"name":"A"}},
  "channels": {"u_1": ["inbox"]},
  "extras":   {"u_1": {"phone":"13800138000"}}
}
```

`vars` / `channels` / `extras` 只在有内容时才写。静态人群的手机号/邮箱走 `extras`。

## 6. 空人群与错误的归宿

| 情况 | 表现 |
|------|------|
| 无 Provider 支持该 scene | `errcode.UnsupportedScene`(40003) → 拆分失败 → 主任务 `failed` |
| Provider 报错（HTTP 5xx、超时） | 拆分失败 → 主任务 `failed`（若非取消/暂停/丢租约） |
| 圈到人但全被过滤 / 全被抽样丢弃 | `wroteAny=false` → `errcode.AudienceEmpty`(40002) → 主任务 `failed` |
| Filter 报 Redis 错误 | 整页失败，同上 |

也就是说，人群侧的任何问题最终都体现为**主任务 failed**，创建接口不会提前报错（除了创建准入）。排查要看 Scheduler 日志 `split failed`。

## 7. 接入自己的人群

三条路，任选：

**A. HTTP（零编译）**

1. 实现 `POST /audience/resolve`：入参 `AudienceQuery`，出参 `AudiencePage`（可在用户 `extra` 里带 `phone`/`email`）。
2. 配 `audience.http.enabled=true` + `url` + `scenes`，并把 `demo_enabled` 关掉。
3. 注意实现分页（`PageToken` 自定义格式即可，平台原样回传）与 `HasMore`。

**B. 实现接口（进程内）**

```go
type MyProvider struct{}
func (p *MyProvider) Name() string { return "crm" }
func (p *MyProvider) Supports(scene string) bool { return scene == "marketing" }
func (p *MyProvider) Resolve(ctx context.Context, q domain.AudienceQuery) (*domain.AudiencePage, error) { ... }

// bootstrap.go：建议在 Demo 之前、Static 之后注册
audReg.Register(&MyProvider{})
```

**C. 运营台 CSV 静态名单（无 Provider）**

1. 人群资产 → 新建 `source=static` → 导入 CSV（phone/email）。
2. 创建活动 → 引用该 `segment_code` → 渠道选短信/邮件。
3. 详见手册 §9.5；Sender 从 `SendRequest.Extra` 取号。

黑名单 / 退订也可用运营台「黑名单/退订」页维护（写 DB 再同步 Redis），不必只靠 redis-cli：

```bash
redis-cli SADD starlink:blacklist u_1 u_2
redis-cli SADD starlink:unsub:sms u_3        # 前缀来自 compliance.unsubscribe_key_prefix
```

## 8. 边界与坑清单

| # | 事实 | 影响 |
|---|------|------|
| 1 | Provider 命中「先注册优先」 | 注册顺序写错会被 Demo 截胡 |
| 2 | 黑名单/退订逐用户 `SIsMember` | 人群大时 Redis 往返量巨大，无 pipeline |
| 3 | Filter 对「未声明 Channels」的用户放行 | **已由 Gateway 偏好/退订终检补齐**；勿再当作合规缺口 |
| 4 | `ab_sample_percent: 0` = 全丢 | 会把活动打成 `failed` |
| 5 | Provider 单页失败即整体失败 | 无页级重试；重拆依赖租约过期 |
| 6 | HTTP Provider 无签名/无重试 | 生产需自建网关兜底 |
| 7 | `ABSampleFilter` 名不副实 | 只看 `Extra["ab_keep"]`，真正抽样在 Splitter |
| 8 | `ComplianceFilter` 是示例实现 | `_block` 后缀规则对真实业务无意义，应替换 |
| 9 | `TotalHint` 只被创建准入用到（`total_hint`/`total`） | Provider 返回的 `TotalHint` 在拆分链路里未被消费 |
