## 1. 状态全图

```text
                    ┌────────────── retry（仅 failed/partial）
                    ▼
create ──► pending ──► running ──┬──► success
             │  ▲        │  ▲    ├──► partial
             │  │        │  │    └──► failed
        pause│  │resume  │  │pause/resume
             ▼  │        ▼  │
           paused ◄──────────┘
             │
   cancel ───┴──► cancelled   （pending/running/paused/retrying 均可取消）
```

`retrying` 是**声明了但没人写入**的状态：它出现在 `TaskStatus` 枚举、`IsPausable`、`IsCancellable`、`ClaimSubTask` 的 WHERE 条件里，但全仓没有任何一处把主任务或子任务更新为 `retrying`。读代码时不要被它误导。

状态判定集中在 `domain`，五个谓词决定了所有 API 的准入：

| 谓词 | 集合 | 用在哪 |
|------|------|--------|
| `IsTerminal` | success / partial / failed / cancelled | 取消幂等、聚合短路、进度 `finished` |
| `IsCancellable` | pending / running / paused / retrying | `CancelMainTask` 的 WHERE |
| `IsPausable` | pending / running / retrying | `Pause` 前置校验 + SQL |
| `IsResumable` | paused | `Resume` 前置校验 |
| `IsRetryable` | failed / partial | `Retry` 前置校验（见文档 03） |

## 2. 创建：`Service.Create`

调用链：`POST /api/v1/campaigns` → `CampaignHandler.Create` → `campaign.Service.Create`。

执行顺序（顺序本身有语义，别调换）：

```text
1. ApplyDefaultChannel(cfg.campaign.default_channel)   // 未传渠道时回填 inbox
2. NormalizeChannels()                                  // 去重 + 校验 + 归一 mode
3. 必填校验 biz_id / biz_scene / audience_ref / template_id
4. Priority.Valid()
5. templates.GetByCode(template_id) 且 Status.Usable()   // 必须 approved
6. GetMainTaskByBizID(biz_id) → 命中即幂等返回
7. ResolvePriority(explicit, biz_scene, mq.high_biz_scenes)
8. checkQuotaAdmission(...)                             // 可能 42901 拒绝
9. CreateMainTask(status=pending, template_body=快照)
   └─ 唯一键冲突 → 回查 biz_id 再幂等返回
```

要点：

- **模板校验早于幂等回查**。已存在的 `biz_id` 若其模板后来被 `disable`，重复创建请求会先在第 5 步拿到 `40903`，而不是幂等返回旧任务。这是当前实现的顺序副作用。
- **幂等不校验内容一致性**。相同 `biz_id` 带完全不同的渠道/模板再次请求，返回的是原任务，新参数被静默丢弃。
- **模板内容做快照**：`TemplateBody: tpl.Body` 落到 `main_tasks.template_body`，之后改模板不影响已创建活动。请求体里的 `template_body` 字段已废弃且被忽略。
- 双重幂等保护：先查后插 + 唯一键冲突回查，覆盖并发创建。

### 2.1 渠道归一化

`domain.CreateCampaignInput.NormalizeChannels()`（[`internal/domain/message.go`](../internal/domain/message.go)）返回 `(主渠道, 渠道链, 模式)`：

| 输入 | 输出 |
|------|------|
| `channel: sms` | `sms`, `[sms]`, `single` |
| `channels: [sms, inbox, sms]` + `mode: single` | `sms`, `[sms,inbox]`, **`fallback`** |
| `channels` 与 `channel` 同时给 | `channels` 生效，`channel` 被忽略 |
| 单渠道 + `mode: parallel` | 归一为 `single` |
| 非法渠道名 / 两个都不传 | `error` → `40001` |

细节详见 [docs/多渠道策略精读.md](多渠道策略精读.md)。

### 2.2 优先级映射

`domain.ResolvePriority`：显式 `high`/`normal` 最高优先；否则按 `biz_scene ∈ mq.high_biz_scenes` 映射；都不命中回落 `normal`。所以「优先级是活动级配置，全局配置只提供默认映射与队列基础设施」。

### 2.3 创建准入 `checkQuotaAdmission`

只在 `channel_quota.enabled=true` 时生效，逻辑：

```text
policy = quota_policy（默认 reject；queue 直接放行）
hint   = audience_extra 中 total_hint / audience_size / total（都没有 → 放行，交给拆分后告警）
for ch in channels:
    若 AdmissionMode(ch) != enforce → skip
    minutes = expected_finish_minutes || channel.target_finish_minutes || 60
    demand  = hint / (minutes*60)
    avail   = AvailableQPS(ch, prio)
    demand > avail 且 avail > 0 → errcode.QuotaExceeded(42901)
```

两个容易踩的点：

- 仓库默认配置里所有渠道都是 `admission: soft`，因此**默认这段逻辑等价于空转**；要生效必须显式改成 `enforce`。
- `42901` 经 `response.Fail` 落到 `40000..50000` 分支 → 返回 **HTTP 400**，不是 429。README 的错误码表也没列这条码。

## 3. 暂停 / 恢复

```go
// Pause
if !task.Status.IsPausable() { return errcode.InvalidState }   // 40902
PauseMainTask: UPDATE ... SET status='paused', version=version+1
               WHERE id=? AND status IN (pending,running,retrying)
```

```go
// Resume
if !task.Status.IsResumable() { return errcode.InvalidState }
hasSubs := task.SubTaskTotal > 0
ResumeMainTask: UPDATE ... SET status=(hasSubs?running:pending), finished_at=NULL, version+1
                WHERE id=? AND status='paused'
```

前置校验 + SQL 条件是双重的：读到的状态可能已过期，最终由 `RowsAffected` 决定成败，失败统一 `40902`。

**`hasSubs` 用 `SubTaskTotal` 而不是真实子任务行数**，这带来一个真实可达的行为：拆分过程中 `sub_task_total` 保持 0（只在收尾写入，见文档 06），此时 pause 再 resume 会回到 `pending`；下一轮 `loopSplit` 会重新抢占并重拆，而 `runSplit` 在拆分前会 `DeleteSubTasksByMainTask` 清掉半成品，所以不会产生重复分片。

暂停在运行时还有两处兜底：

| 位置 | 行为 |
|------|------|
| Scheduler `processSubTask` | 发现主任务 paused → `ReleaseSubTask` 把子任务放回 `pending`（清 worker_id/claimed_at） |
| Pusher `Gateway.Handle` | 返回 `domain.ErrMainTaskPaused` → 不 ACK、留 PEL、**不计入 DLQ**，恢复后继续消费 |

## 4. 取消

```text
Cancel(id)
 ├─ 已终态 → {already_terminal:true}，幂等返回，不动数据
 ├─ CancelMainTask：WHERE status IN (pending,running,paused,retrying) → cancelled + finished_at + version+1
 │    └─ RowsAffected=0（被抢先）→ 重新读一次，按最新状态返回
 ├─ CancelUnfinishedSubTasks：pending/running/retrying → cancelled，last_error='main task cancelled'
 └─ fireWebhook（异步）
```

已经进入 MQ 的消息不会被删除，靠消费侧兜底：

| 位置 | 行为 |
|------|------|
| Scheduler `runSplit` / `Splitter.Split` 循环 | 每页圈人前检查一次，取消则中止并批量取消子任务 |
| Scheduler `processSubTask` | 投递前检查两次（组装前、Publish 前），取消则把子任务标 `cancelled` |
| Pusher `Gateway.Handle` | 写一条 `push_records(status=cancelled)` 占位，然后**正常 ACK**（消息丢弃） |
| Pusher `doSend` 重试循环 | 每次 backoff 后刷新状态，取消则把流水改 `cancelled` |

因此「取消」是尽力而为的软取消：已在途的单条消息不会送出，但已经成功发出的不会撤回。

## 5. 终态如何产生

终态**不由 API 写入**（除 cancel），而是 Scheduler 的 `Aggregator.OnSubFinished` 推进：

```text
OnSubFinished(main, sub, success, fail)
 ├─ TryMarkSubFinished(main, sub)   // Redis SET 幂等，非首次直接返回
 ├─ IncrSubDone → done
 ├─ 主任务已终态 → return
 ├─ UpdateMainTaskStats(..., subDoneDelta=1, status=当前状态)  // 只累加 sub_task_done
 ├─ paused → return（不推进终态）
 ├─ SubTaskTotal<=0 或 done<SubTaskTotal → return（拆分未收尾时也在这里挡住）
 ├─ 读 Redis 累计 succ/fail → final = fail==0?success : succ==0?failed : partial
 ├─ CAS 切终态（冲突则重读一次再试一次）
 ├─ refreshUserCounts：用 push_records 校准 success_count/fail_count
 └─ notifyFinished：goroutine 内发 Webhook
```

关键语义：**流水线终态按「入队成功/失败」判定**。Scheduler 把消息成功写进 MQ 就把子任务标 `success`，所以主任务可能已是 `success` 而渠道还在发。用户级成功/失败另有口径，见文档 02。

`UpdateMainTaskStats` 的两段式设计值得单独记（[`repo/task.go`](../internal/adapter/repo/task.go)）：

```text
第一段：计数无锁原子递增（success_count/fail_count/sub_task_done += delta），不受 CAS 冲突影响
第二段：
  - 非终态：仅当 status=running 时把 pending/running/retrying 推到 running（不覆盖 paused/cancelled/终态）
  - 终态：WHERE id=? AND version=? AND status NOT IN (四个终态 + paused) → 更新 status/version/finished_at
```

这样 CAS 冲突只会丢「状态迁移」，不会丢计数。

## 6. 终态 Webhook

两条触发路径：

| 路径 | 代码 | 说明 |
|------|------|------|
| 取消 | `campaign.fireWebhook` → `webhook.NotifyAsync` | 起 goroutine，10s 超时 |
| 聚合终态 | `aggregator.notifyFinished` → `Notifier.NotifyTaskFinished` | 同样 goroutine + 10s |

URL 解析：活动 `webhook_url` 优先，否则 `webhook.default_url`；`webhook.enabled=false` 时 `NotifyTaskFinished` 直接返回 nil。请求为 `POST` JSON（`domain.WebhookEvent`），带头 `X-Starlink-Event: task.finished`；响应 `>=300` 视为失败。

现状缺口（未修复，来自源码事实）：

- 无签名、无重试、无 outbox 持久化，失败只打一条 `slog.Warn`。
- `webhook_url` 由调用方任意提供且无白名单，存在 SSRF 风险。

事件体里的 `success_count/fail_count` 取自主任务字段，而聚合流程会在发通知**之前**调用 `refreshUserCounts`，所以 Webhook 里看到的是渠道口径（前提是已有 `push_records`）。

## 7. 边界与坑清单

| # | 事实 | 影响 |
|---|------|------|
| 1 | 幂等返回不校验请求内容 | 同 `biz_id` 改参数重发会被静默忽略 |
| 2 | 模板校验在幂等回查之前 | 模板停用后，重复创建会报 `40903` 而非幂等返回 |
| 3 | `retrying` 从未被写入 | 相关分支是死代码 |
| 4 | `Resume` 用 `SubTaskTotal` 判断 | 拆分中途 pause→resume 会退回 pending 并整体重拆 |
| 5 | 取消不撤回已发出消息 | 只保证「未发出的不再发」 |
| 6 | `42901` 返回 HTTP 400 | 客户端不能靠状态码识别配额拒绝，要看 `code` |
| 7 | 终态口径 = 入队结果 | 主任务 `success` ≠ 全部送达；送达看 `push_records` |
| 8 | 所有活动 API 无鉴权 | 任何人可创建/取消/重推 |
